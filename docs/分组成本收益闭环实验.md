# 属性分组成本与结构化收益实验

本轮把分组预处理、上下文编码和 Agent A 推理放进同一成本记录。最终种子可执行性、状态探索和反例发现仍待参数实例化与逐交易回放接口接通后测量；本报告不会以非空模板替代这些指标。

## 输入、方法与复现

预处理使用现有 Hokusai（101 属性）、Request（16 属性）、Immutable（32 属性）的 Slither 属性 JSON。模型对照沿用上一轮固定的 Request 余额相关 5 属性及 Immutable `totalMinted` 相关 18 属性；Hokusai 的一条逐属性输入此前曾被模型服务安全审查拦截，所以没有把它混入重复推理比较。所有模型方案均使用 `gpt-6.1-sol`、同一 Agent A 任务说明、同一属性信息投影、每属性最多一条四调用以内的符号序列及相同 JSON 输出。没有向模型提供项目源码文件访问或工具调用能力。

四种方案：

1. **缓存式逐属性**：每属性一个请求，公共内容置于稳定前缀，属性专属内容随后给出；只算实际返回的缓存 Token，不假定缓存必然命中。
2. **同规模随机批处理**：Request 按 3+2、Immutable 按 6+6+6；每轮固定随机种子重新分配属性。
3. **受控组规模**：组规模与随机方案相同，去掉全组公共特征后按次级状态/动作相似度贪心拆分，成员固定。
4. **当前关联分组**：Request 的 5 条一组，Immutable 的 18 条一组。

每个项目、每种方案、每轮都处理相同属性集合；输入均经过逐条重建与属性 ID 唯一性检查。预设单轮 `输入 Token + 输出 Token` 上限：Request 380,000、Immutable 600,000；所有完整运行均未触顶。预算是统一上限，方法不必耗尽额度。随机种子和逐次提示见[固定对照输入](../.tools/results/分组预算对照输入.json)。三轮按不同方法顺序运行，减少单一顺序造成的缓存优势。

复现入口：

```bash
# Linux Python，已安装的 tiktoken 位于 .tools/tokenizer
python -B func/分组成本基准.py --repeats 9
python -B func/分组预算对照准备.py

# Windows 已登录的 Codex CLI 0.139.0
python -B func/运行分组预算对照.py --case Request
python -B func/运行分组预算对照.py --case Immutable
python -B func/分组预算对照评价.py
```

原始计时在[预处理耗时 JSON](../.tools/results/分组预处理耗时.json)，模型逐次记录在[调用 JSONL](../.tools/results/分组预算对照调用.jsonl)，配对汇总在[评价 JSON](../.tools/results/分组预算对照评价.json)。运行脚本保留既有结果并跳过已尝试请求；仅 `--retry-quota` 会在额度恢复后以原样输入重试额度失败。安全审查拒绝的输入没有改写或重试。

完整运行均覆盖全部目标属性，输出为可解析 JSON，没有重复属性 ID、越界调用长度或超出该属性候选函数集合的调用；所有响应都记录了不确定项。这个检查只说明**结构化格式和候选归属合格**，不说明交易可执行，也不说明安全属性被有效探索。

在相同批次规模下，Request 的受控 3+2 **比随机 3+2 用了更多输入 Token**；Immutable 受控 6+6+6 的输入中位数比随机低约 3.6%，耗时中位数基本相同。当前整组成本最低，主要同时减少了请求次数和重复上下文；它与随机/受控方案**组规模不同**，不能把全部差异归因于依赖关联算法。缓存基线虽然返回一定 `cached_input_tokens`，总输入 Token 和耗时仍高于批处理；服务缓存还包含固定系统前缀，无法从此记录单独推出应用上下文缓存的货币折扣。

人工核对显示，Request 当前整组在第 2 轮对 3 条属性选择空序列，理由是投影中缺少属性最终断言表达式；这种审慎弃答不能简单算作错误。Immutable 整组在三轮中给出 15、16、16 条非空模板，受控拆分给出 16、17、17 条；整组响应没有复用的 `shared_prefix_id`，受控拆分每轮都有至少一个被多属性引用的前缀标识。模型提出的前缀尚未执行验证，不能认定它真实可共享。

## 服务失败与尚未闭合的质量指标

Request 本轮累计 12 次账户额度拒绝和 2 次网络安全自动审查拒绝，失败尝试耗时合计 210.08 秒；额度恢复后仅重试原样输入，安全审查拒绝未重试。这些是服务可用性成本，保存在原始日志中，未混入完整轮次的算法耗时中；若计算实际研究作业的总墙钟时间，必须另行加入。Immutable 未出现服务失败。

参数实例化与原生多交易回放接口尚未接通，故**实际可执行种子数量、失败修复次数和时间、状态探索价值、属性违反发现**均未测量。最终“达到相同有效结果的成本”只能在这些接口可用后，按同一候选预算、同一环境、同一属性集合逐交易回放并计入修复成本来评价。当前结论限于：批处理显著减少本次模型输入和调用次数；同规模受控分组相对随机批处理的增益很小且不稳定；过大的属性组可能降低个别属性的候选覆盖或令模型选择弃答。不能据此宣称分组已改善漏洞发现效率。
