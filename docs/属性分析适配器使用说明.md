# Slither 属性分析适配器：使用与验证记录

主分析程序是 `func/属性分析适配器.py`。它面向**已经包含显式 `echidna_*` 属性的目标合约或测试 Harness**，输出逐属性的静态上下文 JSON，供后续属性条件化和交易种子规划使用。输入可以是单个 Solidity 文件，也可以是 crytic-compile 能构建的项目目录。分析不会编造可执行交易或宣称发现漏洞。五个原生属性项目的复现命令和结果见[五个真实项目属性分析验证](五个真实项目属性分析验证.md)。

## 2026-11-12 通用化改动：先让项目自己编译

优先把**原项目根目录**交给适配器。它先调用 Crytic Compile，由后者识别 Foundry、Hardhat 等项目构建方式和配置，再把编译对象交给 Slither；省略 `--contract` 时会分析所有包含前缀匹配属性的合约。传入项目内的单个 `.sol` 文件时，适配器按 Crytic Compile 的平台探测规则向上寻找项目根，并把该目录作为编译工作目录。默认 `skip_clean=True`，不先清理项目构建产物。

```bash
export PATH="$HOME/miniconda3/envs/contract-fuzz/bin:$PATH"
python func/属性分析适配器.py /path/to/original-project \
  --output /tmp/property_context.json
```

自动解析仍要求项目本身的构建工具和依赖可用。例如 Foundry 项目需要 `forge`。本机无 `forge`，因此本次只验证了配置**探测**：一个临时 Foundry 样本被识别为 `Foundry` 并定位到项目根目录，编译阶段因缺少 `forge` 产生结构化失败报告；**没有验证 Foundry 项目成功编译**。五个最小源码快照没有原项目的构建配置，因此下面的手工 `--solc-remaps` 命令仍作为离线复现实验的后备方式。若自动识别到错误的根目录，可用 `--project-root` 覆盖；`--compile-option NAME=VALUE` 可传 Crytic Compile 选项。

适配器输出 schema `2.0`。顶层 `status` 可为 `complete`、`partial`、`no_matching_property`、`no_matching_contract_or_property` 或 `compilation_or_analysis_failed`；始终写出 JSON，包含输入、已发现/已分析合约、逐属性结果、证据目录、未知项和错误。没有匹配属性时不再以空输出退出；单条属性分析异常时保留该属性的名称、状态读取和 `analysis_status: partial`，其余属性继续分析。编译失败仍返回非零退出码，因为没有可分析的 AST，但失败原因也写入 JSON。

## Slither 源码核查与职责划分

对照本机安装的 Slither 0.11.5、Crytic Compile 源码，以及其[官方 Slither API](https://github.com/crytic/slither/blob/master/docs/src/api/api.md)、[Function 实现](https://github.com/crytic/slither/blob/master/slither/core/declarations/function.py)、[数据依赖实现](https://github.com/crytic/slither/blob/master/slither/analyses/data_dependency/data_dependency.py)和[Crytic Compile 实现](https://github.com/crytic/crytic-compile/blob/master/crytic_compile/crytic_compile.py)检查后，适配器复用以下能力：

| 已有能力 | 当前用法 | 仍需适配器处理的部分 |
| --- | --- | --- |
| Crytic Compile 平台识别、项目编译、编译单元 | `CryticCompile(target)` 后传给 `Slither`；自动记录平台和项目根 | 用户需提供可构建项目；工具链缺失时写结构化失败 |
| Slither `internal_calls`、`library_calls`、`modifiers`、`all_*` 递归查询 | 内部调用边、修饰器、状态读写、外部调用和条件状态读取 | 为每条属性保留到写入点的有界证据路径 |
| SlithIR `HighLevelCall`、`LowLevelCall`、`Index` | 解析多层 typed 调用、保留低层调用未知项与索引 | 跨合约对象别名、动态目标仍未证明 |
| CFG `dominators`、节点后继、数据依赖 `is_dependent` | 守卫、有限路径备选和参数来源 | 求解条件、循环完整路径和交易可执行性 |
| Slither `is_protected()` | 输出 `slither_is_protected_hint` | 该 API 是启发式判断，不能作为权限证明 |

没有加入任何按 Hokusai、Bee、Kink 等项目名或函数名分支的规则。多层调用和未解析调用的处理对所有输入使用同一算法；Slither 也没有直接提供通用的运行时合约对象别名证明，因此适配器显式保留不确定关系。

## 环境与运行命令

本次验证使用已有 WSL 环境：Slither 0.11.5、Python 3.11、solc 0.4.25。没有安装新工具。以下命令在 V2 项目根目录执行：

```bash
export PATH="$HOME/miniconda3/envs/contract-fuzz/bin:$PATH"
export SOLC_VERSION=0.4.25

python func/属性分析适配器.py sol/DSToken属性适配.sol \
  --contract DSTokenPropertyHarness \
  --solc-remaps "ds-math/=sol/ds-math/ ds-auth/=sol/ds-auth/" \
  --output /tmp/dstoken_property_context.json

python func/属性分析适配器.py sol/WETH9属性适配.sol \
  --contract WETH9PropertyHarness \
  --output /tmp/weth9_property_context.json
```

对其他真实项目，先使用项目自身可正常工作的编译环境，再指定**包含属性的合约**；例如：

```bash
python func/属性分析适配器.py /path/to/project \
  --contract PropertyHarness --output /tmp/property_context.json
```

同名合约可加 `--contract-source` 指定源码路径片段。额外的 crytic-compile 编译参数可通过重复的 `--compile-option NAME=VALUE` 传入；`--solc` 和 `--solc-remaps` 分别用于编译器路径和导入映射。大型项目可调整 `--max-call-depth`、`--max-setup-depth` 和 `--max-paths`；达到上限会在结果中标记。运行 `python func/属性分析适配器.py --help` 可查看全部参数。

## JSON 如何使用

`properties` 按属性分开，记录属性读到的状态、索引表达式、环境读取、候选交易入口和前置状态闭包。`candidate_actions` 中的 `effect_ids` 指向顶层 `effect_catalog`，避免多个属性重复保存同一份证据。每条 effect 包括：

- 具体写入表达式、源码位置和 mapping/数组索引；
- 从外部入口到写入函数的调用链，以及内部调用的参数绑定；
- 控制流中的必要守卫 `guards` 和分支备选 `cfg_guard_alternatives`；
- 守卫的状态读取、参数数据依赖、内部谓词返回路径及外部调用；
- 写入表达式所调用的数学/库函数的成功返回约束 `expression_call_constraints`。

例如 DSToken 的 `mint(uint256)` 调用 `mint(address,uint256)` 时，绑定为 `guy = msg.sender`、`wad = wad`；后者写入余额时受 `auth` 和 `stoppable` 修饰器约束。`auth` 内部的 `isAuthorized` 分别有合约自身、owner 和外部 authority 授权等返回路径。`add` 内部的溢出检查也被记录。`transferFrom` 写余额前保留两条控制流路径：一条要满足 allowance 检查，另一条绕过该检查；两条均经过余额检查。

`prerequisite_state_closure` 记录守卫读取的状态、声明初始化表达式、构造函数写入者，以及可能改变该状态的外部函数。这里的 `possible_setup_actions` 是**可选建立路径**：若部署初始状态已满足守卫，不一定需要先执行这些函数。结果不把所有写入者强行串成交易序列。

`unresolved_effect_actions` 单列没有解析到直接状态写入、但包含外部调用或内联汇编的入口。这些入口可能通过回调或动态效果影响属性；分析器不会把它们悄悄丢掉，也不会直接宣称它们确实影响属性。

`cross_contract` 记录属性通过 typed high-level call 读取的外部合约状态，并沿 Slither 已解析的目标函数继续展开多层调用。`observations` 保留属性侧调用、状态和 `external_route`；`candidate_actions` 包含跨合约候选及其 `effect_ids`；`prerequisite_states` 记录候选守卫读取的状态。候选的 `matched_observations.relation` 为 `same_static_receiver` 或 `state_overlap_alias_unproven`；后者只说明同一 Slither 状态变量出现在读写两侧，调用对象是否相同仍未知。`alias_unproven_observations`、`unmatched_observations`、`unresolved_observations` 分别保留别名未证明、无已解析写入入口、目标函数体未知的观察。`opaque_call_candidates` 列出低层调用等可能有间接效果的入口，状态为 `opaque_effect_possible_no_property_link`，**不表示已证明它会影响该属性**。

每条属性还有 `analysis_class`：`stateful_context_available` 表示至少找到一个本合约或跨合约候选，**不表示全部观察均已覆盖，也不代表别名已证明**；`stateful_dependency_unresolved` 表示观察到持久状态但没有状态关联候选，`dependency_unknown` 表示只有无法解析的外部观察，`stateless_or_input_only` 表示没有识别到持久状态依赖。这是静态输出的分类，不是执行可达性或分析准确率的认证。`unknowns` 按属性记录无法确定的信息；读取候选时仍须检查各条证据和未匹配观察。

`evidence_summary` 便于筛选候选：分别计数候选关联、带写入点证据的关联、别名未证明的关联、未匹配观察和未解析调用入口。报告即使标为 `complete`，也只表示静态处理没有中断；生成种子前仍需按这些字段检查证据强弱。

| 项目 | DSToken 属性适配 | WETH9 属性适配 |

| 每条属性的候选外部入口 | 9 | 5 |
| 第一条属性的前置状态项 | 4：`DSAuth.owner`、`DSAuth.authority`、`DSToken.stopped`、`DSToken.balanceOf` | 1：`WETH9.balanceOf` |

此前遇到的版本问题是 Slither 文档示例里的 `from slither.analyses import is_dependent` 在本机 0.11.5 不可导入；程序改用实际安装版本的 `slither.analyses.data_dependency.data_dependency.is_dependent`。DSToken 导入依赖仍使用前次核验过的单个 `--solc-remaps` 参数。程序生成的 JSON 放在指定输出位置；本次验证输出仅放在 `/tmp`，没有增加结果目录。

## 边界与下一步使用判断

这份输出比 Slither `--print echidna` 的函数级读写关系更细，但**不是任意真实合约的完整执行语义**。五项目通用化复核中，31 条原生属性有 24 条取得至少一个候选，其中一部分只按目标状态变量重叠关联；1 条有状态依赖仍无状态关联候选，但保留了未解析低层调用入口；6 条是无状态/仅输入检查。`unknowns` 明确标记 mapping 键别名、外部授权返回值、合约 ETH 余额来源、循环或分析上限等问题。特别是 `balanceOf[dst]` 是否影响属性读取的 `balanceOf[address(0)]`，仍需参数求解或执行验证。代理合约、动态调用、复杂汇编和外部协议状态也必须结合实际部署与测试环境处理。

若原始合约没有符合“零参数、返回 bool”的显式属性，适配器会输出 `no_matching_property` 及已发现合约信息；不能把上次添加的诊断属性当作上游原生属性。下一步生成种子时，应把 `guards` 和各条 `cfg_guard_alternatives` 当成待满足的约束，再进行 ABI 校验、原生多交易执行和回放。
