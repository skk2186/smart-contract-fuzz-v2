# Slither 属性分析适配器：使用与验证记录

主分析程序是 `func/属性分析适配器.py`。它面向**已经包含显式 `echidna_*` 属性的目标合约或测试 Harness**，输出逐属性的静态上下文 JSON，供后续属性条件化和交易种子规划使用。输入可以是单个 Solidity 文件，也可以是 crytic-compile 能构建的项目目录。分析不会编造可执行交易或宣称发现漏洞。真实项目的来源和验证结果见[真实项目属性分析验证](五个真实项目属性分析验证.md)。

## 原生项目编译与属性源码定位（2026-11-12）

优先把**原项目根目录**交给适配器。Hardhat 等项目直接由 Crytic Compile 执行原生编译；Foundry 项目先读取其 `forge config --json` 的 `src`、`test`、`script` 路径，只用属性函数声明定位相关 `.sol` 文件，再逐文件交给 Crytic Compile 原生定向编译和 Slither 分析。每个 Foundry 定向编译使用独立临时输出目录，避免多个 build-info 混淆；不会按照项目名写分析规则。省略 `--contract` 时分析所有匹配前缀的属性合约。直接传入项目内 `.sol` 文件时，自动寻找项目根作为编译工作目录。默认 `skip_clean=True`。

```bash
export PATH="$HOME/miniconda3/envs/contract-fuzz/bin:$PATH"
python func/属性分析适配器.py /path/to/original-project \
  --output /tmp/property_context.json
```

自动解析仍要求项目自身工具和依赖可用。已在 V2 目录的 `.tools` 中安装 Linux Node 22.16.0、项目锁定依赖对应的 Hardhat 2.28.3，以及经官方签名校验的 Alpine 版 Forge 1.9.0-dev；Slither 0.11.5、Crytic Compile 0.3.11 使用原有 Python 环境。完整 Hokusai 与 Immutable 项目现已按各自原生配置构建成功，并由适配器分析，结果见下文。最小源码快照无项目构建文件时，`--solc-remaps` 仍是后备方式。若自动识别到错误根目录，可用 `--project-root` 覆盖；`--compile-option NAME=VALUE` 传递 Crytic Compile 选项，`true`/`false` 会转换为真正的布尔值。

适配器输出 schema `3.1`。顶层 `execution_status` 区分 `success`、`partial`、`failed`；`status` 进一步给出 `complete`、`partial`、`no_matching_property`、`no_matching_contract_or_property` 或 `compilation_or_analysis_failed`。每条属性独立给出 `analysis_status`（是否完成静态处理）、`context_status`（是否有带写入点的候选上下文）和 `dependency_status`（静态依赖已闭合、带限制、未闭合或未知）。每条还具有 `property_id`、`analysis_contract`、`analysis_contract_source`：继承的同名属性在不同测试合约中有不同 ID。顶层 `complete` **只表示程序完成**，不是属性上下文完整。没有匹配属性、单条属性失败或编译失败时仍写出 JSON；单条属性异常保留源码位置、已读状态、读取点、调用点、该属性未知项和异常，继续处理其余属性。多个 Foundry 属性文件中若只有一份编译失败，`source_issues` 保留异常及 Crytic Compile 捕获到的原始 `compiler_log`（包括 Solidity 编译诊断），其余属性仍输出，进程返回非零状态码。

## Slither 源码核查与职责划分

对照本机安装的 Slither 0.11.5、Crytic Compile 源码，以及其[官方 Slither API](https://github.com/crytic/slither/blob/master/docs/src/api/api.md)、[Function 实现](https://github.com/crytic/slither/blob/master/slither/core/declarations/function.py)、[数据依赖实现](https://github.com/crytic/slither/blob/master/slither/analyses/data_dependency/data_dependency.py)和[Crytic Compile 实现](https://github.com/crytic/crytic-compile/blob/master/crytic_compile/crytic_compile.py)检查后，适配器复用以下能力：

| 已有能力 | 当前用法 | 仍需适配器处理的部分 |
| --- | --- | --- |
| Crytic Compile 平台识别、项目编译、编译单元 | Hardhat 根目录或 Foundry 属性源码交给 `CryticCompile(target)`，再传给 `Slither`；记录平台和项目根 | Foundry 根目录按原生路径配置分别编译属性文件；工具链或单个源码失败时保留真实错误 |
| Slither `internal_calls`、`library_calls`、`modifiers`、`all_*` 递归查询 | 内部调用边、修饰器、状态读写、外部调用和条件状态读取 | 为每条属性保留到写入点的有界证据路径 |
| SlithIR `HighLevelCall`、`LowLevelCall`、`Index` | 解析多层 typed 调用、保留低层调用未知项与索引 | 跨合约对象别名、动态目标仍未证明 |
| CFG `dominators`、节点后继、数据依赖 `is_dependent` | 守卫、有限路径备选和参数来源 | 求解条件、循环完整路径和交易可执行性 |
| Slither `is_protected()` | 输出 `slither_is_protected_hint` | 该 API 是启发式判断，不能作为权限证明 |

没有加入任何按 Hokusai、Bee、Kink 等项目名或函数名分支的规则。多层调用和未解析调用的处理对所有输入使用同一算法；Slither 也没有直接提供通用的运行时合约对象别名证明，因此适配器显式保留不确定关系。

## JSON 如何使用

`properties` 按属性分析上下文分开，记录属性读到的状态、索引表达式、环境读取、候选交易入口和前置状态闭包。以 `property_id` 区分不同分析合约继承的同名属性；只用 `property` 函数名作键可能合并不同测试场景。`candidate_actions` 中的 `effect_ids` 指向顶层 `effect_catalog`，避免多个属性重复保存同一份证据。每条 effect 包括：

- 具体写入表达式、源码位置和 mapping/数组索引；
- 从外部入口到写入函数的调用链，以及内部调用的参数绑定；
- 控制流中的必要守卫 `guards` 和分支备选 `cfg_guard_alternatives`；
- 守卫的状态读取、参数数据依赖、内部谓词返回路径及外部调用；
- 写入表达式所调用的数学/库函数的成功返回约束 `expression_call_constraints`。

每条属性还单列 `evidence_ids`。顶层 `effect_catalog` 仅保留被至少一条已输出属性引用的证据；若某条属性中途失败，不会把它的孤立中间证据混入其他属性。

例如 DSToken 的 `mint(uint256)` 调用 `mint(address,uint256)` 时，绑定为 `guy = msg.sender`、`wad = wad`；后者写入余额时受 `auth` 和 `stoppable` 修饰器约束。`auth` 内部的 `isAuthorized` 分别有合约自身、owner 和外部 authority 授权等返回路径。`add` 内部的溢出检查也被记录。`transferFrom` 写余额前保留两条控制流路径：一条要满足 allowance 检查，另一条绕过该检查；两条均经过余额检查。

`prerequisite_state_closure` 记录守卫读取的状态、声明初始化表达式、构造函数写入者，以及可能改变该状态的外部函数。这里的 `possible_setup_actions` 是**可选建立路径**：若部署初始状态已满足守卫，不一定需要先执行这些函数。结果不把所有写入者强行串成交易序列。

`unresolved_effect_actions` 单列没有解析到直接状态写入、但包含外部调用或内联汇编的入口。这些入口可能通过回调或动态效果影响属性；分析器不会把它们悄悄丢掉，也不会直接宣称它们确实影响属性。

`cross_contract` 记录属性通过 typed high-level call 读取的外部合约状态，并沿 Slither 已解析的目标函数继续展开多层调用。每个属性观察点有独立 `observation_id`、调用源码、接收者路径和状态定义。读写匹配**逐观察点**进行，不能把同一状态变量定义下的全部观察合并。`matched_observations.relation` 为 `confirmed_static_path` 时，属性和候选从同一根合约出发，所有接收者跳转都由相同的状态槽定义及源码位置静态定位；这是符号路径关联，`runtime_object_proven` 仍为 `false`。仅有目标状态变量定义相同、但接收者路径不同或不能定位时，关系为 `possible_instance_alias`，候选状态为 `possible_instance_alias_candidate`。不能解析目标的调用放在 `unresolved_observations` 或 `opaque_call_candidates`，并保留调用位置；这类入口状态为 `opaque_effect_possible_no_property_link`，**不表示已证明它会影响该属性**。

`prerequisite_states.possible_writers_by_definition` 仅表示这些函数会写同一**状态定义**，并附有 `instance_relation` 和 `source_route`；它们不是同一部署实例的已证明前置交易。守卫同时保留 `state_read_definitions`，含定义源码位置，避免同名变量跨文件混淆。`property_write_states` 标记属性函数自身的状态副作用；这类属性检查也可能改变测试状态。

每条属性还有 `analysis_class`：`stateful_context_available` 表示至少找到一个本合约或跨合约候选，**不表示全部观察均已覆盖，也不代表别名已证明**；`stateful_dependency_unresolved` 表示观察到持久状态但没有状态关联候选，`dependency_unknown` 表示只有无法解析的外部观察，`stateless_or_input_only` 表示没有识别到持久状态依赖。这是静态输出的分类，不是执行可达性或分析准确率的认证。`unknowns` 按属性记录无法确定的信息；读取候选时仍须检查各条证据和未匹配观察。

`evidence_summary` 便于筛选候选：分别计数候选关联、带写入点证据的关联、别名未证明的关联、未匹配观察和未解析调用入口。报告即使标为 `complete`，也只表示静态处理没有中断；生成种子前仍需按这些字段检查证据强弱。

## 边界与下一步使用判断

这份输出比 Slither `--print echidna` 的函数级读写关系更细，但**不是任意真实合约的完整执行语义**。六项目的最小源码快照共 63 条原生属性：55 条有写入点候选证据，2 条只有状态观察，6 条无状态或仅输入；这些数值与上述完整项目结果有重叠，不应相加。带证据的候选也可能只是别名未证明的可能关联。Immutable 的 32 条属性中有 4 条属性函数自身写入状态，已单列为未知风险。`unknowns` 明确标记 mapping 键别名、外部授权返回值、合约 ETH 余额来源、循环或分析上限等问题。特别是 `balanceOf[dst]` 是否影响属性读取的 `balanceOf[address(0)]`，仍需参数求解或执行验证。代理合约、动态调用、复杂汇编和外部协议状态也必须结合实际部署与测试环境处理。

若原始合约没有符合“零参数、返回 bool”的显式属性，适配器会输出 `no_matching_property` 及已发现合约信息；不能把上次添加的诊断属性当作上游原生属性。下一步生成种子时，应把 `guards` 和各条 `cfg_guard_alternatives` 当成待满足的约束，再进行 ABI 校验、原生多交易执行和回放。
