# Phase 20：初始状态与前置条件驱动的跨交易种子验证

## 目标与结论

本阶段针对 Phase 19 暴露的通用缺口，补充部署初始状态观察、静态前置条件候选链、失败分类和 Agent A 有限重规划。固定回归使用 OpenNFTs 的 `echidna_owner`、`echidna_balance` 及 Request 的 `echidna_token_conservation`；Kink 的 `echidna_token1_conserved` 作为留出样本。未修改合约或属性，也未加入按项目名称分支的逻辑。

固定样本最终运行中，OpenNFTs 两属性、Request 一属性和 Kink 留出属性各生成 1 条 Anvil 可执行种子；4 条均被 Echidna 加载、回放并产生变异证据。OpenNFTs owner 属性被种子触发；Request 与 Kink 的守恒属性仍 passing。OpenNFTs balance 虽完成 mint 状态变化，但没有把 NFT 铸给谓词检查的目标地址，因此不能算作严格的属性目标状态到达。整体说明初始状态、真实角色和多交易依赖的处理有所改善，但数值反馈的闭环、参数/状态绑定和严格目标路径测量仍不充分，不能据 4 个小样本声称稳定泛化。

## 实现改动

1. `func/功能/属性种子上下文.py` 保留 Slither 守卫中的状态读取、谓词调用及数据依赖；从源码可见的 helper 调用补充候选状态写入，并把守卫状态与潜在生产动作连接为 `prerequisite_dependencies`。依赖标记为静态候选，不代表已证明可达。另提取构造器片段和构造期间调用的候选动作。
2. `func/功能/种子验证.py` 增加 Anvil 初始状态观察：在快照内重新部署 Harness，采集公开 view getter、Echidna 布尔属性、简单单参数 view 守卫探测，并恢复快照。识别 `owner/admin/governor/controller/operator/manager/guardian` 等公开角色 getter，将非零真实角色地址并入本属性 sender pool。私有映射和未公开状态仍不能直接观察。
3. `deepseek/AgentA.py` 在规划提示中加入构造器已初始化信息、部署态、候选前置链、真实角色及按失败类别重新选择/插入准备动作的规则。
4. `deepseek/AgentB.py` 允许本属性观察到的角色地址作为 sender，并为有限长度 `string` 参数添加 ABI 种子序列化，以支持动态字符串入口。该限制为 UTF-8 128 字节。
5. `deepseek/实验过程/运行Agent种子流程.py` 对 Anvil 回放失败分类，并允许最多一次 Agent A 执行后重规划。Request 记录显示内部调用 revert data 是标准 Solidity `Error(string)`；增加通用解码后，原始 `Insufficient refundable amount` 证据可归为 `numeric_constraint`。另将上下文合并表达式改为 Python 3.8 兼容写法，以适配仓库实际 WSL 运行时。

## 实验设置与结果

样本、属性 ID 和执行政策在实现前记录于[实验方案](../deepseek/结果/Phase20前置依赖验证/实验方案.json)。每属性最多 1 个候选、8 步、1 次 Agent A 规划修复、1 次 Agent B 参数/执行修复和 1 次 Agent A 执行后重规划；Echidna `testLimit=80`、`seqLen=8`、单 worker。方案预算为 80000 Token；OpenNFTs 中间运行在该预算下遇到预算预检失败，最终回归统一使用 100000 Token。这一预算偏离已保留记录，因此结果不是严格同 Token 预算下的配对估计。每次运行的模型调用、种子、Anvil 逐笔证据、Echidna 日志及 LCOV 保存在[逐次结果目录](../deepseek/结果/Agent种子语料/)。API 密钥留在本地配置，未进入代码或结果。

| 样本 | 既有失败对照 | Phase 20 最终运行 | Anvil 目标动作状态建立 | Echidna 回放结果 |
|---|---|---|---:|---|
| OpenNFTs `echidna_owner` | 0/1；重复初始化/固定 sender 或参数校验问题 | 1/1，`transferOwnership(address)` | 1/1 | 1 条加载、回放；属性被触发失败，771 unique instructions 后提前终止 |
| OpenNFTs `echidna_balance` | 0/1；`transferFrom` 因 `Invalid token ID` 回滚 | 1/1，`mint(string)` | 1/1（mint 有状态变化） | 1 条加载、回放；属性 passing，5052 unique instructions |
| Request `echidna_token_conservation` | Phase 19 固定失败记录为 0/1；第一次 Phase 20 运行也为 0/1 | 1/1，`driver_chargePayment` → `driver_refundPayment` | 1/1 | 1 条加载、回放；属性 passing，18758 unique instructions |
| Kink 留出 `echidna_token1_conserved` | 已有对照为 1/1 | 1/1，`singleSidedAdd` → `yankLiquidity` | 1/1 | 1 条加载、回放；属性 passing，10632 unique instructions |

表中的“目标动作状态建立”沿用预先约定的 operational proxy：计划末步成功且产生预期状态变化。它不是属性分支覆盖率。特别是 OpenNFTs balance 的谓词检查 `_other` 地址，而 `mint(string)` 将 token 铸给调用者；实际目标地址余额没有建立，故该属性严格目标状态仍为 0/1。属性 passing 也不等于深层目标分支已覆盖。

OpenNFTs Phase 19 原生 Echidna 80-test 对照为 owner 5041、balance 5026 unique instructions，均未加载外部种子。本阶段 owner 因种子触发属性失败而提前停测，771 不应与完整 80-test 数值直接比较；balance 的 5052 比既有记录多 26，但随机种子不同且只有单次运行，不能推断为稳定覆盖收益。Request 的首次 Phase 20 无种子运行得到 11726 unique instructions，最终有种子运行得到 18758；两者 Echidna seed 分别为 20261122、20261127，仅作方向性观察。历史 Phase 12 的 Request 曾有有效种子，而 Phase 18/19 固定回归再次失败，说明 Agent/采样表现有运行波动，本报告不把 Request 的单次成功表述为稳定提升。

本阶段新发生的 DeepSeek 调用累计 143851 tokens，按接口返回 usage 和记录价目估算 off-peak $0.019782660。统计含中间失败与最终运行；逐次 API usage 和原始结果保留在对应运行目录。

## 失败案例与因果边界

- OpenNFTs 中间运行 `e938…` 的 owner 计划使用从 `owner()` 读出的 `address(42)`，但 Agent B 仍以固定 sender 列表校验，种子被拒；balance 属性第二次规划触发 80k Token 预算预检。后续通用 sender pool 和更充足的实验预算后，两条最终种子均通过 Anvil。原失败没有删除。
- Request 首次 Phase 20 序列在退款步骤因 `Insufficient refundable amount` 内部回滚；旧分类把 hex revert data 当成普通执行失败，Agent A 重规划一次后仍失败。保存的同一 Anvil trace 经通用 `Error(string)` 解码重分类为数值约束失败。修正后再运行 Request 产生有效两步序列，但该最终运行的首个计划直接成功，没有实际触发 Agent A 重规划；因此它验证了生成有效种子的可能性，不是对“数值反馈驱动重规划能修复该案”的单独因果证明。
- Kink 首次留出调用在 API 之前因 Python 3.8 不支持字典 `|` 合并而失败，0 API tokens。最小兼容修正后 Kink 生成并回放成功。Kink 成功运行发生在基于 Request trace 的 revert 分类补丁之前；后补丁仅影响失败交易分类，未以 Kink 结果调节规划机制。留出结果仍是单次小样本。

## 适用范围与瓶颈

当前方法对公开 getter 可观察的初始状态、简单 owner/admin 身份、构造期已完成初始化、可由候选动作生产的对象/状态，以及 Agent B 支持的基本 ABI 参数类型较适用。它能把这些信息带入有限长度的多交易计划，并在 Anvil 逐笔回放后保存失败轨迹。

主要瓶颈是：Slither 状态生产者图仍是启发式候选关系，不能证明调用可达、别名一致或生产动作成功；getter 探测只覆盖公开可读和少量简单参数，无法得知私有映射及事件/返回值生成的真实 ID；当前动态角色识别只匹配少量命名 getter；数值边界仍主要由模型猜测，Request 的可退款余额说明已有分类不等于可以合成满足约束的金额；失败闭环最多重规划一次；错误分类覆盖标准 `Error(string)` 和常见词汇，尚不能普遍解析 custom error、panic 或复杂 trace；字符串支持仅解决 ABI 序列化，不能自动选择正确 recipient。当前路径指标只看末步状态变化，需增加与目标谓词实际状态相关的检查。

## 下一阶段建议

1. 优先把 Anvil trace、revert reason、守卫表达式和已观察状态统一成结构化约束，区别缺少对象、身份、余额/额度和 ABI 类型错误，并将已解码的 `Error(string)`、custom error 参数、panic selector 纳入证据。
2. 为跨笔数据建立可验证绑定：从事件、成功回执、getter 或状态差分中提取新 ID、owner、授权额和退款余额，再把这些实际值传给后续步骤；避免只根据计数器静态推测。
3. 将 guard 数值条件转换为边界/关系约束（如 `refund <= refundable`、`amount > 0`、fee 上限），先用 getter/回放状态求值，失败时基于新状态重新求参并允许有限重规划。
4. 改进目标路径指标：针对属性引用的状态定义运行时可观测目标谓词，分别报告目标动作成功、目标状态建立、属性被触发/反例发现和指令覆盖；不要用末笔任意状态变化替代深层分支到达。
5. 用更多未参与开发的合约做预注册、小规模、多随机种子重复，并保持相同 Echidna seed 与预算的配对对照；先检验可重复性，再扩大覆盖实验。
