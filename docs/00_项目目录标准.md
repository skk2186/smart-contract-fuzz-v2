# 00 项目目录标准

本文档定义智能合约模糊测试 V2 仓库的强制目录规则。新增内容先按用途归类，再决定路径；不得为单个项目临时发明平行目录。遇到本规范未覆盖的内容时，优先放入最接近的既有类别，并在确有长期复用价值时再扩展标准。

## 一、根目录

根目录只保留项目级入口、配置和以下已定义目录，不放临时脚本、实验输出或散落的合约源码。

| 路径 | 唯一用途 |
|---|---|
| `AGENTS.md` | 本项目持续适用的协作与目录约束 |
| `docs/` | 使用说明、研究记录和可复现的实验报告 |
| `func/` | 属性分析及其他可复用功能代码、验证脚本 |
| `sol/` | 单合约样本和真实项目 Solidity 源码 |
| `deepseek/` | DeepSeek 专属接口、Agent 实现及对应实验材料 |
| `seeds/` | 外部生成或待执行的 Echidna 原生种子及元数据 |
| `crytic-export/` | Crytic Compile 生成的项目导出物 |
| `.tools/` | 本地工具、缓存和私密配置；默认不提交凭据 |

允许必要的版本控制和项目工具配置文件留在根目录。若新增根目录项，应是项目级必需项，而不是为了方便临时放置的文件。

## 二、文档 `docs/`

1. 文档使用 `两位数字_中文主题.md` 命名，例如 `01_Slither环境复现.md`。
2. 新文档使用尚未占用的下一个编号；已有文档被引用或记录实验时，不因插入新内容而重排编号。
3. 文档应记录可复现所需的信息：目的、输入/环境、实际命令、遇到的问题及解决方式、真实结果、限制和关联产物。
4. 纯临时笔记、重复说明和没有证据支撑的结论不进入 `docs/`。实验原始日志和机器生成结果放在对应结果目录，文档链接到它们。
5. 中文主题名应具体、简洁；仅在工具或项目正式名称中保留英文名。

## 三、功能代码 `func/`

```text
func/
├── 功能/       # 可复用的分析、转换、验证和上下文构造实现
└── 测试过程/   # 回归测试、验证脚本、基准脚本、实验驱动脚本
```

- 生产功能代码放在 `功能/`，不得与测试/实验脚本混放。
- 测试和实验脚本放在 `测试过程/`；如需新增子目录，必须对应长期、稳定的类别，不能按每次运行创建目录。
- 可复用实现留在 `func/`，DeepSeek API 或 Agent 的专属封装留在 `deepseek/`。
- 不保留 `__pycache__`、临时编译输出、无用副本或一次性调试文件。

## 四、合约源码 `sol/`

```text
sol/
├── 单合约测试/
│   └── <合约名>/       # 一个独立样本及其必要依赖
└── 真实项目/
    └── <项目名>/       # 一个真实项目的母目录
        └── ...         # 保留上游必要的原始多层结构
```

- 单独用于适配器、回归或方法测试的合约，按合约名放入 `单合约测试/<合约名>/`；其编译必需的辅助源码随该样本归档。
- 来源于真实协议/仓库的代码放入 `真实项目/<项目名>/`。即使项目源码原本分布在多个目录，也必须统一收纳在项目母目录下，并尽量保留上游相对布局、配置和许可证信息。
- 不同项目的同名合约不能仅按合约名合并；项目来源边界必须清晰。
- 不为特定合约编写硬编码分析分支。真实项目不能编译时记录原始错误和环境，不得静默修改源码掩盖问题。
- 下载或复制源码时记录来源、版本/提交和必要的许可证信息；不要把生成物误当成上游源码。

## 五、DeepSeek 内容 `deepseek/`

```text
deepseek/
├── AgentA.py / AgentB.py / DeepSeek 接口实现  # 专属调用与协议代码
├── 实验过程/                                      # DeepSeek 专属驱动和复现实验脚本
└── 结果/                                          # 请求记录、成本、种子、回放及报告产物
```

- 只有与 DeepSeek 调用或其结果直接相关的内容放在此处。与模型无关的通用分析、种子验证、回归工具仍放在 `func/`。
- 不复制通用模块来避免导入；通过稳定的项目内模块引用复用。
- API Key、访问令牌和其他秘密不得写入源代码、文档、日志、种子元数据或 Git。仅从受保护的本地配置/环境变量读取。
- 请求日志应先检查并脱敏，不能记录密钥或授权头。
- 一次实验的输入、配置、成本和结果保持可追溯；不保留无法解释来源的孤立输出。

## 六、种子、导出物与本地工具

- `seeds/` 保存完整的多交易种子、目标属性/来源元数据及必要的版本信息。按项目和实验用途归类，避免以单次运行时间无限创建目录。
- `crytic-export/` 是 Crytic Compile 的导出/中间产物区域，不手工混入源码或文档；只有复现所需产物才纳入版本控制。
- `.tools/` 保存本机专用二进制、缓存或私密配置。凭据文件必须受 Git 忽略规则保护；代码不得依赖某位研究者机器上的绝对路径。
- 原始实验结果、汇总报告和可复现脚本各归其位，不互相复制整份文件。

## 七、命名、移动与维护

1. 目录名优先使用稳定、可读的中文类别名；源码和工具要求的名称、ABI 标识、上游目录名可保留原名。
2. 文件名应表达内容，不使用“新建文件”“最终版2”“临时”等不稳定名称。
3. 移动文件时同步检查 Python 导入、相对路径、Slither/Crytic Compile 参数、Echidna 配置、文档链接及结果索引。
4. 不因整理目录改变实验逻辑或上游源码。需要修改行为时单独说明并验证。
5. 整理完成后检查重复文件、空目录、断开的引用、密钥泄漏和 Git 忽略状态；仅报告实际检查过的项目。
6. 未获用户明确指令，不修改历史 V1 仓库、不提交或推送 Git，也不借目录整理扩大为实验或代码重构。

## 八、推荐结构示例

```text
项目根目录/
├── AGENTS.md
├── docs/
│   ├── 00_项目目录标准.md
│   └── 01_主题说明.md
├── func/
│   ├── 功能/
│   └── 测试过程/
├── sol/
│   ├── 单合约测试/
│   │   └── <合约名>/
│   └── 真实项目/
│       └── <项目名>/
├── deepseek/
│   ├── 实验过程/
│   └── 结果/
├── seeds/
├── crytic-export/
└── .tools/
```
