## 2. 根因诊断

### 2.1 首笔金额下界

`Streams.sol` 中 `_minAmtPerSec = (_AMT_PER_SEC_MULTIPLIER + cycleSecs - 1) / cycleSecs`，`_AMT_PER_SEC_MULTIPLIER = 1,000,000,000`。冻结配置给出 `cycleSecs = 10`，因此真实下界为 `100,000,000`。`_setStreams` 要求 `amtPerSec >= _minAmtPerSec`。Agent 输出的 `amountPerSec = 1,000`，比下界少 `99,999,000`（仅为要求值的万分之一），原始 Foundry 回放首笔 `setStreams` 回滚，原因是 `Stream receiver amtPerSec too low`，目标断言未到达。

E2 原实现只支持由 getter 支持的上界修复；没有消费 Solidity `require` 中的数值下界、`minAmtPerSec()` getter 与回滚文本，也未把被修复参数传播到依赖该参数的属性调用。

### 2.2 账户 ID 映射

`EchidnaConfig.getAccount(uint8 rawId)` 通过 `uint256(rawId) / 64` 取账户槽位。因此 raw ID 0 和 1 都映射到 USER0；USER1 对应 raw ID 64。Agent 把 0、1 当成两个不同账户，和原生账户语义不符。该问题不是首笔回滚的直接原因，但会使 Agent 对角色分离的理解错误。人工诊断把接收方 ID 从 1 改为 64 后，两笔交易都成功；自动 E2 只修复数值下界，没有自动改账户 ID。

### 2.3 E3、Phase37 与上下文

Phase41 E3 对失败回放的生成入口从插入位置 1 开始，没有为首笔失败提供位置 0 的生产者插入；并且过往的共享状态相关性容易占用候选预算。Phase42 保留“先处理首个失败、仅用 guard 读取与候选写入的精确状态交集”的约束；金额下界失败交给 E2。G2 只有在 writer/reader 约束精确匹配后才调用 Phase37 参数绑定。

冻结 Agent 上下文 JSON 为 958,499 字节，包含 48 个候选动作上下文；本阶段筛选后为 15 个直接相关候选动作。原上下文虽出现 `getAccount(uint8)` 名称，但不含 `rawId / 64` 映射实现；也没有 `_minAmtPerSec`、`amtPerSec >= _minAmtPerSec` 和运行时 `minAmtPerSec()` 观测。过滤后上下文将这些映射、范围和 guard 证据纳入，体积为 400,502 字节。模型未重跑，因此这只证明上下文证据结构得到补齐，不能证明 Agent 理解效果改善。

E1 的两个调用只存在显式参数复用关系，没有 Phase37 所需的真实跨交易写状态→guard 读状态匹配。故 G2 的 24 个候选均记录 `not_applicable_no_matching_cross_transaction_constraint`，不是绑定算法失败。

## 4. 通用修复与自动回放

1. E2 增加由匹配的源码数值 guard、运行时 getter 与“过低”回滚证据共同支撑的下界修复；原上界修复保留。仅修复有证据证明的 ABI 数值参数，并仅向声明了 `data_dependencies` 且字段名匹配的后续参数传播。
2. 属性上下文保留 ABI 范围、直接相关候选动作、辅助函数调用链、账户映射和数值 guard 证据；不明确的关系维持 unknown。
3. E3 对首笔 state-precondition 失败允许在 index 0 插入生产者；要求候选写状态与失败 guard 读状态精确相交。普通数值下界失败不再消耗 E3 候选预算。
4. G2 的 Phase37 绑定只在真实跨交易状态约束匹配时启动；Drips 本任务无匹配，状态如实记为不适用。
5. E3 反馈汇总现在从完整逐笔轨迹中取最近一次实际目标属性检查，避免属性调用后面的普通交易把已观察结果覆盖为 unknown。修正后的 G1/G2 汇总从保存的原始 V2 反馈重算，没有重新执行交易；原汇总和 Foundry 原日志均保留。

自动 E1 仍在首笔回滚。自动 E2 从同一份冻结 Agent 输出把两个 `amountPerSec` 参数从 1,000 修复为 100,000,000；修复依据包含 `Streams.sol:921` 的 `amtPerSec >= _minAmtPerSec`、getter 实测值 100,000,000 和原始回滚原因。两笔交易都成功，目标属性交易成功并由 Foundry 记录 passing；该结果不是反例，`counterexample_state_established=false`。属性内部 `getSqueezableAmount` 的 before/after 操作数仍不可观察，不能把“断言通过”解释成状态目标已建立。

## 6. 结论与边界

本阶段达到工程修复目标：Phase41 首笔失败根因为金额低于源码下界；自动 E2 能依据 guard/getter/回滚证据修复参数并使完整序列和原生 Echidna seed-only 回放成功。账户 ID 映射错误已明确提供给属性上下文，但没有重跑 Agent，故没有 Agent 自动纠正证据。E3 可执行序列中属性均 passing，没有目标反例；G2 与 G1 序列相同、绑定不适用。未执行 500 预算 Echidna fuzz 对照，也未测独立项目。
