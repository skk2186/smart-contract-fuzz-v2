# Phase30B：目标可达性与多交易规划修复

日期：2026-11-19；执行分支：`main`；开始 HEAD：`96ade661d7ffef5b80b040a0f069afe38533dbd4`

## 结论摘要

冻结的 `WalletHarness.echidna_wallet_accounting_respected()` 在原始 Wallet 逻辑和五账户 Harness 下真实可达。隔离的人工诊断 Oracle 通过四笔交易令账户 1 累计提款达到 2 ETH、累计存款保持 1 ETH；Anvil 属性由真变假，Echidna 回放同一四笔语料后报告属性反例。

Phase30A 未生成目标序列的直接可证原因包括：Agent A 输入的同名函数源码匹配忽略合约名和 ABI 签名；属性观察器没有展开有界循环中的公开映射 getter；Agent B 的一次修复只改了参数，没有改变交易步骤；Echidna 统计器把回放交易计数报告成变异证据。Slither 对跨合约传递写入的输出也为空，是已观察到的分析局限。人工 Oracle 证明共享 Wallet 和重复退款是到达目标所需的状态关系；但不能仅凭这次规划失败断言模型内部的唯一原因。

本轮实施了一次通用修复并完成冻结预算内的一次新规划。新规划拿到了正确源码和跨合约调用链，属性 getter 也开始逐交易观测，但 Agent A 仍选择 `deposit → withdraw`，实际参数为等额存取，目标未到达。该种子和 Phase30A 两种参数化均能由 Anvil 和 Echidna 完整回放，三者都没有违反属性。按预注册门槛，没有运行 G0/G1/G2 的 500 次模糊测试分组，也没有追加 Agent 调用或第二轮算法改动。

Wallet 已用于开发、人工诊断和方法修复。本结果只能计入机制诊断，不能计为独立留出实验或 V2 自动发现。

## 2. 人工目标可达性 Oracle

Harness 构造函数只创建一个 `Wallet`，并将同一个实例传入五个 `WalletUser`。`Wallet.refund()` 将 `balances[msg.sender]` 转出，但不清零该记账值。下列序列先由账户 1 留下 1 ETH 的 Wallet 内部余额，再由账户 0 注资 1 ETH；账户 1 的两次退款遂依次从共享 Wallet 提取 1 ETH。

| 步骤 | 发送账户 / actor | 交易与金额 | 执行 | Wallet 余额 | actor 1 Wallet 内部记账 | 五账户累计存款 / 提款（actor 0；actor 1；actor 2–4） | 属性 |
|---|---|---|---|---:|---:|---|---|
| 初始 | — | 部署原 Harness | 成功 | 0 ETH | 0 ETH | `0/0; 0/0; 0/0` ETH | 真 |
| 1 | `0x0000000000000000000000000000000000020000` / actor 1 | `deposit(1)`, 1 ETH | 成功 | 0 → 1 ETH | 0 → 1 ETH | `0/0; 1/0; 0/0` ETH | 真 |
| 2 | `0x0000000000000000000000000000000000010000` / actor 0 | `deposit(0)`, 1 ETH | 成功 | 1 → 2 ETH | 保持 1 ETH | `1/0; 1/0; 0/0` ETH | 真 |
| 3 | `0x0000000000000000000000000000000000020000` / actor 1 | `refund(1)`, 0 ETH | 成功 | 2 → 1 ETH | 保持 1 ETH | `1/0; 1/1; 0/0` ETH | 真 |
| 4 | `0x0000000000000000000000000000000000020000` / actor 1 | `refund(1)`, 0 ETH | 成功 | 1 → 0 ETH | 保持 1 ETH | `1/0; 1/2; 0/0` ETH | **假** |

完整地址、交易哈希、调用 trace、五个 actor 的逐步 ledger、私有映射读取方式和源码哈希均在 [manual-oracle-result.json](../func/测试过程/SCFuzzBench公开项目接入/结果/Wallet02Refund/Phase30B-20261119/diagnostic-oracle/manual-oracle-result.json)。其中 actor 1 的 `cumulativeDeposits=1 ETH`，最终 `cumulativePayout=2 ETH`；actor 0 的共享资金注入不增加 actor 1 的属性存款额。

Echidna 2.3.2 在独立的 `manual-diagnostic-oracle.txt` 上加载 1 条、回放 1 条，并输出 `Test echidna_wallet_accounting_respected falsified!`；退出码 1 是预期的属性失败。Anvil 与 Echidna 对相同四笔反例结论一致。启动失败的前两次 Echidna 尝试也保留在同目录的 `echidna-attempt-01/02` 日志；它们发生在交易回放之前，第三次补齐已有 Python / Foundry 工具路径后成功。

## 3. Phase30A 根因分析

| 观察到的问题 | 类别 | 已验证事实 | 根因判断边界 |
|---|---|---|---|
| Agent A 得到错误的动作源码 | 静态上下文构造 | `_function_excerpt` 只按函数名扫描并返回第一个匹配；旧上下文把 Harness 的 `deposit(uint8)`、`refund(uint8)` 配成 `WalletUser.deposit()`、`WalletUser.refund()`，漏掉 Harness 的 actor 映射和账本更新。 | 这是已确认的实现缺陷，会削弱序列规划证据。 |
| Slither 没有跨层状态链 | 静态分析 | Phase30A 报告有直接候选动作和读写状态，但 `cross_contract.observations` 及 helper effects 为空；报告没有从 Harness 经代理到 Wallet 的写入链或共享实例关系。 | 分析输出缺口已确认；它对 Agent 结果的贡献有明确机制依据，但不能说是唯一原因。 |
| Agent A 规划少了共享资金来源和重复退款 | 序列规划 | 原序列只有 actor 0 的一次 `deposit → refund`，两笔后 payout 等于 deposit；未包含另一账户供资，也未重复同一退款。人工 Oracle 证明这两类操作在当前目标下有意义。 | 失败行为已确认。模型为何没采用其它候选属于推断；这次新规划仍选 `withdraw`，说明新增源码线索尚不足以保证正确路径。 |
| Agent B 无法补齐缺失步骤 | 参数生成 / 执行反馈 | Phase30A 的一次反馈将 deposit 从 1 ETH 改为 0.001 ETH，函数顺序仍为两笔 `deposit → refund`。 | 已确认：该反馈通道修参数，不负责 Agent A 序列重规划。 |
| 属性相关 getter 未记录 | 执行反馈 | 谓词读取 `cumulativePayout[i]` 和 `cumulativeDeposits[i]`；两者在 Harness ABI 中都是公开单参数 getter。旧回放的 `initial_predicate_getters` 和逐笔 getter 列表为空。 | 已确认的 getter 解析缺陷：原解析支持直接调用与无参标识符，不支持有界数组/映射索引。 |
| 首轮交易资金不足 | 运行环境 | 初始余额为 `4294967295 wei`，高于该余额的存款交易报 `Insufficient funds`；统一改为 100 ETH 后，旧序列完整成功。 | 环境混杂因素已确认；它解释首轮 Anvil 失败，不解释候选未达到目标。 |
| `mutation_evidence=true` | 统计口径 | Phase30A 日志显示 `tests: 0/1`、`fuzzing: 3/1`、语料回放 1/1；输出 coverage 交易语义等同输入 seed，没有新序列或 seed 外新增 coverage。 | 已确认统计器错误地把正的 fuzzing 计数当作变异。现在只记录 fuzzing 活动；没有输入/输出 coverage 或序列差集时 `mutation_evidence=false`。 |

## 4. 一次最小通用修复

修复沿用既有链路，不增加 Agent、搜索器、覆盖贪心调度或重规划框架：

1. [属性种子上下文.py](../func/功能/属性种子上下文.py) 现在按合约名和 ABI 签名选择动作源码；遇到不唯一匹配会返回空，不再取第一个同名函数。它为 receiver 类型可从源码声明解析、目标方法唯一的调用补充有界 `source_call_chain`，并附相关构造函数和类型声明。对象别名仍只作为源码证据，未解析或运行时不确定关系不被声称为已证明。
2. [AgentA.py](../deepseek/AgentA.py) 加入通用规则：沿已解析调用链检查状态关系；若源码证据支持重复操作、持久调用者状态与共享资源约束，可在现有 8 步上限内考虑前置供资或重复操作，并标记尚未执行验证的假设。规则没有 Wallet 函数名、账户索引、金额或人工序列。
3. [种子验证.py](../func/功能/种子验证.py) 识别属性中的公开单参数映射 / 数组 getter，并解析小于等于 256 项的静态有界整数循环。回放每个交易前后会记录各索引 getter 值；无法解析的边界或表达式留作 unresolved，不猜值。
4. 同一文件的 Echidna 统计解析器把 `fuzzing` 活动、`tests` 状态和属性失败分别记录；仅凭日志计数不声明变异。Phase30A 的 `tests: 0/1` 现被记作状态快照，不解释为目标到达或变异次数。

非 Wallet 回归使用既有 Request 候选 `c451c4279019-01-token_conservation_charge_then_refund`，不生成新模型候选。改后 Anvil 两交易回放状态为 `executable`，初始属性 getter 有 15 项；Wallet 源码上下文则显示 `WalletHarness → WalletUser → Wallet` 的具体动作链和构造函数共享关系。调用链是按源码类型声明、函数名和参数个数做的有界静态解析，不等同于编译器完整调用图；别名、复杂重载和运行时对象身份仍需执行证据核验。机器记录见 [01-通用实现回归结果.json](../func/测试过程/SCFuzzBench公开项目接入/结果/Wallet02Refund/Phase30B-20261119/01-通用实现回归结果.json)。

## 6. 对研究问题的回答

1. **Wallet 目标是否真实可达？** 是。独立人工 Oracle 在四笔交易后令属性为假；Anvil 和 Echidna 对同一序列一致。
2. **V2 原来为何没有生成有效序列？** 已确认源码上下文同名误配、Slither 跨层关系输出缺失、映射 getter 未观测、Agent B 只改参数以及 `mutation_evidence` 统计偏差。Agent A 的序列行为已确认漏掉目标所需步骤；模型没有选择正确路径的内在原因仍不能唯一归结。运行余额不足另为已排除的环境因素。
3. **本轮修改了什么？** 通用、按源码和 ABI 驱动的合约 / 函数匹配与有界调用链，上下文中的重复状态操作规则，属性映射 getter 观察，有界属性循环解析，以及保守的 Echidna 统计字段。
4. **通用还是样本特定？** 实现规则通用，不包含 Wallet 名称、退款标签、账户索引、具体金额或人工序列；Request 旧种子两交易回归通过。
5. **自动 seed 是否达到目标？** 否。P1 `deposit → withdraw` 在两个引擎都完整执行 / 回放，但属性保持为真。人工 Oracle 不计自动发现。
6. **相较旧版哪些改善？** 新上下文对 Wallet 三层动作源码匹配正确，跨合约关系与属性 getter 的逐笔值可观察；Request 历史 seed 回放仍正常。目标到达率没有改善（P0/P1 都未达），新 getter 和正确源码上下文也未改变本轮候选的结论。没有进行 fuzz coverage 比较。Token 与用时不是同条件配对收益。
7. **是否有论文机制证据？** 有限的机制诊断证据：证明目标由跨账户共享资金与持久内部记账共同决定，并定位原上下文 / 观察盲区。它是单个公开已知样本上的人工 Oracle 与负向自动规划结果，只能支持方法局限和测量口径讨论，不能支持方法有效性或独立泛化主张。
8. **下一步是否做独立公开样本验证？** 建议是。下一次研究阶段应选此前未参与 Wallet 开发或诊断的公开样本，冻结输入后检验通用调用链与属性观察修复；本轮未自动启动该阶段。鉴于 P1 仍未达到 Wallet 目标，不应把这次代码修复宣称为已证明的规划能力提升。
