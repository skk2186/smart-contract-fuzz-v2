# 属性分组的 Token 与 Agent A 成本对照

## 对照范围与复现

本轮只比较上下文组织与 Agent A 序列规划，不改变原生安全属性集合，不接入 Agent B 或 Echidna。输入为 Hokusai 101 条、Request 16 条、Immutable 32 条属性的现有 Slither 适配器 JSON，以及[属性关联分组输出](../.tools/results/属性关联分组.json)。生成脚本在 `func` 中，结果保存在 `.tools/results` 中。

```bash
# 已安装环境的 Python，tiktoken 0.14.0 放在 .tools/tokenizer
python -B func/属性上下文压缩.py
python -B func/AgentA对照准备.py

# Windows 已登录的 Codex CLI 0.139.0；脚本按原样提示运行 gpt-6.1-sol
python -B func/运行AgentA对照.py --all --case Request
python -B func/运行AgentA对照.py --all --case Immutable
python -B func/AgentA结果评价.py
```

Hokusai 有一次逐属性请求被模型服务自动拒绝，因此没有把 `--all --case Hokusai` 作为重跑命令。原始调用结果见[Agent A 调用记录](../.tools/results/AgentA调用记录.jsonl)；固定输入见[Agent A 对照输入](../.tools/results/AgentA对照输入.json)，结构化评价见[Agent A 对照评价](../.tools/results/AgentA对照评价.json)。重跑脚本会跳过已有成功调用，但不会自动跳过曾被拒绝的输入。

## 第一步：相同信息的三种布局

先从每条属性的 JSON 构造固定的 **Agent A 任务投影**：保留属性身份、源码位置、读写状态、环境信息、观察点、候选函数及其效果 ID、跨合约观察与未知别名、前置状态闭包、未知项，以及关联效果的写入表达式、调用路径、守卫、CFG 守卫路径和源码位置。辅助性 `interpretation`、`evidence_summary` 与效果里的部分扩展调用列表未进入任务投影；因此这里的“等价”指三种布局对**同一任务投影**等价，不等于完整原始 JSON 字节无损。这个投影本身仍可能缺少属性最终 `return` 表达式或运行时语义，模型响应已指出这种不足。

三种布局分别是：① 每条属性连同关联效果上下文独立展开；② 项目级 `context_blocks` 和效果目录只出现一次，属性仍逐条列出引用；③ 每个关联组有自己的共享目录，组内属性逐条列出引用，跨组不隐式共享。构造器逐属性重建并比较任务投影，同时核验全部候选动作、未知项、效果来源、调用路径、守卫表达式及 CFG 守卫路径。核验计数见[完整压缩结果](../.tools/results/属性上下文压缩结果.json)：149 条属性、510 个候选动作项、532 个未知项、470 个被引用的效果，以及 27,199 次守卫/路径出现均进入重建检查。这里的数字包含重复出现，不代表不同函数或不同守卫的数量。

使用 `tiktoken 0.14.0` 的 `o200k_base` 对最紧凑 JSON 文本计数；这是**发送内容的 Token 计数**，不含模型系统提示、工具协议或缓存计费。每种布局的任务投影与 JSON 编码方式相同。

| 项目 | 逐属性展开 | 项目级去重 | 当前分组 | 分组相对逐属性节省 | 最大单次输入：逐属性 / 项目级 / 分组 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Hokusai | 3,950,565 | 1,383,857 | 3,476,303 | 12.0% | 216,685 / 1,383,857 / 221,758 |
| Request | 675,493 | 100,153 | 438,356 | 35.1% | 55,490 / 100,153 / 66,431 |
| Immutable | 304,591 | 107,247 | 135,705 | 55.4% | 37,376 / 107,247 / 43,425 |
| 合计 | 4,930,649 | 1,591,257 | 4,050,364 | 17.9% | — |

项目级去重在三个项目上都是更小的**逻辑下界**，但 Hokusai 的单次 138 万 Token 无法作为本轮模型请求；其一些逐属性/分组输入也超过 20 万 Token。若把项目级目录在多次独立请求中重复发送，实际账单也不会等于该表中的一次计数。当前分组的实用收益来自把同一组放进较少模型请求，并非其压缩率优于全项目去重。没有为压进上下文而悄悄删除属性或守卫。

## 第二步：代表属性的真实推理

固定模型 `gpt-6.1-sol`、固定中文任务说明、每属性最多一条四调用以内的符号序列、相同 JSON 输出目标。模型不得调用工具或读文件，实际记录的工具项为空。选择 Hokusai `EchidnaRewardVestingVault` 的 4 属性组（共享 `createSchedule` 准备动作）、Request 余额相关的 5 属性组（静态闭包无共同准备动作），以及 Immutable 由 `totalMinted` 连接的 18 属性大组。Immutable 另用确定性启发式去掉全组公共特征后，按次级特征贪心拆为三个 6 属性小组；属性集合完全相同。针对每个**只含一个原组**的代表案例，“项目级去重”和“组内去重”的输入字节相同，所以只调用一次模型，避免伪造独立对照。

Request 组输入相对逐属性累计输入少 73.4%；Immutable 大组少 85.0%，三个小组少 75.2%。这是本次调用的观测，不是服务价格或更广泛项目的效果估计。全部成功响应均为可解析 JSON，属性 ID 无重复或越界，所提调用均属于相应属性的候选函数集合，且都记录了不确定条件。组内共享前缀标识是模型的提议，不是执行验证结果。Request 两种布局多次提出 `driver_chargePayment → driver_refundPayment`，尽管静态闭包没有共同准备动作；源码显示 `driver_chargePayment` 内部会铸币、授权并尝试扣款，但 `try/catch` 允许内部失败，因而还不能认定随后退款有效。Immutable 大组比逐属性少给出 2 条非空候选，小组拆分恢复到 16 条，说明通用计数器形成的大组可能压低个别属性的候选覆盖；这仍不是有效种子数量的比较。

## 执行性与结论边界

Agent A 按原技术分工只生成函数顺序、符号参数条件和发送者角色；本轮没有实际 ABI 参数、具体发送者与确定性交易回放。因此**实际可执行候选序列数量为“未测量”**，不能填 0，也不能把上表的非空候选数当作可执行数。要回答这一项，必须对同一批模板进行一致的参数具体化和逐交易回放，并把该开销计入总预算。当前证据支持“分组减少了 Request 和 Immutable 代表样本的模型调用与输入 Token”，同时显示“大组可能牺牲候选覆盖”和“全局去重在纯文本上更省，但会遇到上下文窗口限制”。
