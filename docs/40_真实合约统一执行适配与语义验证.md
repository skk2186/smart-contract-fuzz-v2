# Phase40：真实合约统一执行适配与语义验证

## 目标与范围

Phase40 在正式运行 V2 算法前建立固定版本真实合约的准备、执行和准入机制。核心算法、E2/E3、Phase36 门控和 Phase37 参数绑定保持不变；Drips 是工程回归样本，不计入论文独立样本。本轮只检查 Drips 与一个独立候选 Strata。

统一适配器位于 `func/功能/真实合约统一执行适配器.py`，准入入口位于 `func/测试过程/SCFuzzBench公开项目接入/Phase40真实合约适配验证.py`。项目 manifest 固定上游 commit、递归 submodule SHA、源码树哈希、Solidity 版本、remappings、Harness/属性、账户、部署参数、观察器和执行后端。准备阶段验证 Git 状态、tracked 源码与依赖哈希，并把源码及已固定依赖缓存到 `.tools/cache/real-contracts/`；重用 workspace 缓存前也逐个校验 tracked 文件哈希，发现偏差时从固版归档重建。支持 lockfile SRI 锁定的归档依赖；失败后记录缺失路径、固定 SHA、获取方式和错误，默认抑制重复获取，只有显式设置 `--retry-failed-archives` 或 `--retry-missing-submodules` 才重新尝试。正式项目准入只接受 `ready` 或 `ready_with_verified_adapter`。

## Drips：原生 Harness 与语义验证

Drips 固定 commit `c50d160ead6bf82b1d1071e853dc74da0b23f595`，recursive tracked source tree SHA-256 为 `fc1b15ff0b5caa5ea2aa624f8d6cf0c51354ca87402891288921b6d2e809f0a0`；六个递归 Git submodule 均匹配固定 gitlink SHA。使用 solc 0.8.20、Foundry 1.9.0-dev 与 Echidna 2.3.2。上游 `Echidna` Harness、业务源码和原生 Assertion 属性未修改。

Foundry Cheatcode 后端在隔离驱动中部署了原始 Harness 类型并回放三笔交易：`give(0,64,1e18)` 由 USER0 执行；`addStreamImmediatelySqueezable(0,64,0)` 由 USER0 执行，Harness 内部 `hevm.warp` 推进 1 秒；`testSqueeze(64,0)` 由 USER1 执行。三笔调用均成功，配置的 `invariantAccountingVsTokenBalance()` 每步检查通过。状态观察显示接收方 `splittable` 从 `1e18` 增至 `1e18 + 1`；逐笔 sender、参数、value、结果、返回数据、时间和状态观察见 [Foundry 逐笔 TSV](../func/测试过程/SCFuzzBench公开项目接入/结果/Phase40-20261121/Drips/drips-prank-warp-squeeze.foundry.tsv) 与 [V2 反馈](../func/测试过程/SCFuzzBench公开项目接入/结果/Phase40-20261121/Drips/drips-prank-warp-squeeze.v2-feedback.json)。

随后 Echidna 原生 Assertion 后端加载同一三笔固定语料（1 条），回放成功；`testSqueeze(uint8,uint8)` 与 `invariantAccountingVsTokenBalance()` 均为 passing，未观察到属性失败。原生日志和语料分别保存在 [Echidna 日志](../func/测试过程/SCFuzzBench公开项目接入/结果/Phase40-20261121/Drips/drips-prank-warp-squeeze.echidna-native.log) 和 `Drips/echidna-corpus/drips-prank-warp-squeeze/coverage/`。

这是一致结果的可核验证据，不表示两个后端提供等量观测：Foundry 产生逐调用状态与时间轨迹，但 Harness 内嵌调用不是独立 mined transaction，没有逐调用 receipt，gas 是估值；Echidna 原生 replay 给出 corpus replay 与断言结果，但没有输出相同粒度的逐笔 getter/时间轨迹。因此跨后端核对了相同序列和相关属性结果，时间变化及 `splittable` 数值由 Foundry 轨迹直接验证，没有声称 Echidna 独立报告了这些值。Phase39 普通 Anvil 对原始 Drips Harness 的部署回滚日志保留为历史对照；RPC sender impersonation 不实现 Harness 内部 `hevm.prank/warp`，不能作为等价替代。

最终机器准入结果为 `ready_with_verified_adapter`。此状态证明该 manifest 下的固定源代码、离线构建、原生 Harness cheatcode 执行、交易反馈和属性检查通过；它不把 Drips 计作独立论文实验。

## Anvil 回归与独立候选

为验证原 Anvil 执行入口没有被适配层破坏，Wallet 使用冻结的 `deposit(0)`（value `1e15`）与 `refund(0)` 序列回归。修复通用 Python vendor 路径优先级后，两笔交易均在 Shanghai hardfork 配置下成功，Wallet 属性前后均为真，累计存款与累计派付均为 `1e15`。之后同一冻结 spec 与 sender 映射通过统一 `AnvilRpcBackend` 接口重放，两笔交易、部署与状态观察再次通过；驱动和 V2 反馈保存在 `Wallet-Anvil/run-unified-backend-regression.py` 与 `Wallet-Anvil/unified-backend/`。Anvil 提供真实交易 receipt、区块号和 gas，但该回归没有内部 prank/warp，也不能据此推断 Anvil 支持 Drips 语义。Phase39 runner 增加通用 `hardfork` 配置透传，Wallet 执行器改动不涉及合约源码。

只读兼容性检查对象 Strata 固定 commit `51ad892ed5a7c73df8b64e5a11c6c5371037b2d6`，递归 tracked source tree SHA-256 为 `f2915e18cd21c5b2ebe9793a90b0ab92738d623660e6818a7113ed5aeaee2ec2`，所有已下载 submodule 均匹配。锁文件 SHA-256 校验通过，但缺少 `node_modules/@openzeppelin/contracts@5.3.0` 与 `@openzeppelin/contracts-upgradeable@5.3.0` 两个固定归档。仅尝试了 lockfile 中的 HTTPS URL，Python urllib 报 TLS unexpected EOF，WSL curl 报 `SSL_ERROR_SYSCALL`；归档 SHA-512 SRI 已记录，未使用浮动版本或修改源码。准入结果为 `dependency_blocked`，未进入构建、Harness 或执行阶段。详细尝试和错误见 [恢复尝试记录](../func/测试过程/SCFuzzBench公开项目接入/结果/Phase40-20261121/Strata/01c-package-restore-attempts.json) 及 [机器准入结果](../func/测试过程/SCFuzzBench公开项目接入/结果/Phase40-20261121/Strata/admission-result.json)。本轮未更换第三个项目。

## 统一接口与 V2 反馈边界

`ExecutionBackend` 统一暴露部署、序列执行、属性检查及 V2 反馈转换。Foundry 后端用 `vm.prank`、`vm.warp`、`vm.roll` 保留测试进程内部 cheatcode 语义；Anvil 后端复用 Phase39 的 RPC runner，并显式标记它不能提供内部 cheatcode。遇到不支持的 absolute timestamp、block number、独立 `tx.origin` 或没有配置 sender 映射时返回 `unsupported_semantics`，不会改写交易请求伪装成功。Echidna 原生后端复用固定 harness/config 和语料回放。

当前反馈可为 E2 提供交易函数、参数、sender、value、成功/失败、可得回滚字节、时间以及配置 getter 的前后状态；Foundry 逐调用 gas 只是估值。Foundry 生成驱动当前支持整数、地址、布尔、字符串和十六进制 bytes 标量参数；动态数组、tuple/struct 参数会明确返回 `unsupported_semantics`，不会用错误编码继续运行。E3 可以读取通用逐步 getter 差值和逐步属性结果，但项目 predicate 到 getter/键/角色的专属映射仍由 manifest 配置，当前没有完整通用化为 V2 的 `target_property_state` 轨迹；E3 不是无需配置即可直接消费的完整 drop-in 接口。不可观察的状态或失败原因不会补造。

准入入口每阶段保存机器 JSON 与原始日志，终态包括 `ready`、`ready_with_verified_adapter`、`unsupported_semantics`、`dependency_blocked`、`execution_failed`、`unknown`。没有序列、属性、观察器或执行证据的情况不会被提升为 ready。Drips 与 Strata 配置、状态和原始阶段产物见 [Phase40 结果目录](../func/测试过程/SCFuzzBench公开项目接入/结果/Phase40-20261121/)。

## 结论与限制

- 统一的固定源码/依赖准备、Foundry cheatcode、Anvil RPC、Echidna 原生后端和准入格式已实现；Drips 达到 `ready_with_verified_adapter`，Wallet Anvil 回归通过。
- Drips 原始 Harness 在支持 cheatcode 的 Foundry 后端完成真实部署、三笔有效状态交易、原生属性检查与 V2 反馈；Echidna 对固定序列回放并报告相关断言通过。
- 逐笔反馈足以供 E2 现有交易执行信息使用；E3 的通用状态变化可用，但 predicate/getter 轨迹仍需 manifest 映射，不能称为完整即插即用。
- 已具备新真实项目正式实验的工程准入基础，但必须先完成项目 manifest、固定依赖准备、属性/观察语义核验及参数类型兼容检查。Strata 因两项固定 npm 归档无法获取而阻塞，不能进入正式实验。
- Foundry Cheatcode 后端没有逐笔 mined receipt，Echidna 没有相同粒度的状态轨迹；两者只能报告实际共同核验的属性和序列结果。没有运行 Agent A/B、G0/E1/G1/G2 或 Phase41。

源码完整性复核（Drips、Strata 树哈希与 Wallet 历史冻结源码/Harness 哈希）见 `func/测试过程/SCFuzzBench公开项目接入/结果/Phase40-20261121/source-integrity.json`。机器准入结果和原始日志保留在同一 Phase40 结果目录。本阶段完成后停止增加功能。
