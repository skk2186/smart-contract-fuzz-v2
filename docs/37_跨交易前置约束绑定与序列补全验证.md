## 2. Phase36 原始失败轨迹与参数修复审查

逐项查看了 Phase36 `SafetyMissingPrerequisite` 下的 G1 原始候选回放 JSON。三类场景的扩展器都插入了预期函数，但 Phase36 中 `_replay_candidate` 调用 `_repair_once` 后没有产生参数修复提案：失败交易的 `runtime_constraint_observations` 为空、`constraint_repair_proposal` 为空，候选记录的 `parameter_repair` 也为空。

| 任务 | 原始插入候选 | 消费交易失败 | 修复为何没有绑定前置操作 |
|---|---|---|---|
| B | `createTask → configureTask(1) → executeTask(3)` | `LIMIT_EXCEEDED` | Slither guard 已表达 `amount <= executionLimit`，但旧修复器依赖失败交易的运行时 getter 观察和参数/输出名称匹配；该失败记录没有运行时观察，且修复器只改失败交易的数值参数，不能回写插入的 `configureTask.maxAmount`。 | 
| C | `fundCredit → authorizeOperator(owner) → executeFor(owner,1)`；授权调用者是 owner | `NOT_AUTHORIZED_OPERATOR` | 消费者 `msg.sender` 是 operator，但写入的授权值是 owner。旧修复器只提数值参数修复，不能把消费者 sender 与授权 mapping 值关联；本例也没有运行时 mapping 观察。 |
| D | `mint → approve(owner,10) → transferFrom(owner,recipient,4)`；消费者 sender 是 spender | `ALLOWANCE_TOO_LOW` | `approve` 把 owner 授权给了 owner，消费者读取的是 `allowance[owner][msg.sender]`。旧修复器没有 allowance mapping 键观察，也不修地址角色；故无参数提案。 |

因此问题不是“旧修复器完全不运行”：它确实在候选失败后运行一次，但没有生成可执行修复。失败来自跨交易约束未连通，并且修复目标和时机不合适：需要在执行前改新插入的 writer，让其满足后续 consumer 的 guard；只在执行后尝试修改失败 consumer 的数值参数不够。

原始逐候选轨迹保持在 [Phase36 SafetyMissingPrerequisite 目录](../func/测试过程/跨交易属性状态依赖审计/结果/Phase36-20261120/SafetyMissingPrerequisite/)。其中包括候选序列、逐笔 Anvil 状态、失败文本、运行时观察及修复提案字段。

## 3. 通用绑定能力核查

当前 HEAD 已有 `func/功能/跨交易状态约束.py::bind_inserted_prerequisite`，Phase36 `_run_g2` 也有 `binding_enabled` 可选参数，但默认值为 `false`，Phase36 正式 G2 未启用该绑定分支。因此本轮没有重复添加同一实现，也没有修改 E3 核心代码。

该函数使用 Slither `effect_catalog` 中的 writer 表达式、consumer guard 和 state read 集合，并结合 ABI 输入和实际消费者交易的 sender/参数，在 Anvil 回放前只修改新插入的 writer。当前实现把候选解限制为每个 writer/consumer 关系最多一个，不枚举完整 Oracle 序列。

冻结后保存的[静态推导证据](../func/测试过程/跨交易属性状态依赖审计/结果/Phase37-20261121/01-Phase36候选静态约束推导.json)对 Phase36 G1 原始候选逐条运行该绑定函数，记录了每条候选的绑定状态、前后参数、guard、mapping key 和 ABI 来源：

- B：22 条含 `configureTask` 的候选中，17 条能从 guard `amount <= executionLimit` 推导 `maxAmount >= 3`；代表候选把 `maxAmount` 从 1 改为 3。
- C：2 条含 `authorizeOperator` 的候选中，1 条在消费者之前；它把授权 mapping 的 owner 索引对齐到 consumer 的 owner，并把授权值从 owner 改为 consumer `msg.sender`（operator）。
- D：21 条含 `approve` 的候选中，6 条能匹配 consumer 的双层 allowance key；代表候选保留 owner 发送者，把 spender 改为后续 `transferFrom` 的实际 sender，并把额度从 10 改为 4。

这些数字仅描述静态绑定提案，不能解释为 Anvil 完整成功、目标状态到达或安全属性反例。没有把独立 Oracle 序列读入算法。

Phase36 门控缓存以候选操作和父状态指纹共同判定：只有父状态指纹可观测且与先前探测一致时才复用跳过结论；状态不同或不可观测时重新探测。该规则符合本轮的父状态一致性要求，未修改门控。

## 5. 结论与停止决定

1. **是否把 0/3 的缺步骤补全结果提高？** 没有可核验的提升。正式 G1/G2 未运行，当前仍不能把 Phase36 的 0/3 改写为成功；Phase37 的 Anvil 完整执行成功数为未测，而不是 0/3 或 3/3。
2. **机制针对的通用问题是什么？** 当前代码路径能从“writer 写入的状态键/值”与“后续 consumer guard 读取的状态键/值”建立绑定，包括数值边界、mapping 索引、`msg.sender` 角色和 allowance spender。三个固定开发任务的静态推导均出现正向提案；执行前置关系是否经 Anvil 稳定成立仍未验证。
3. **是否值得进入论文方法？** 可保留为候选方法模块，但现有结果还不足以宣称论文贡献。需要在同一冻结预算下完成 G1/G2 Anvil 对照，随后复测 Wallet、Phase36 门控和至少两个合格留出任务，才能判断是否值得写入核心方法。

按停止规则，本轮到此停止：不做逐合约硬编码，不扩大真实项目，不启动 fuzz campaign，也不进入 Phase38。
