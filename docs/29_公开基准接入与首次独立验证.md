# 29 公开基准接入与首次独立验证

## 结论先读

本阶段没有让任何一个全新公开项目完成 V2 的完整链路。Origin Dollar 是唯一跑到原生测试与 V2 静态分析的项目：Harness 编译成功，Echidna 原生测试运行成功，但属性状态依赖分析不完整，Anvil 部署探针返回失败收据且修复诊断代码后未能重跑。因此没有 Agent 种子、没有 G1/G2，也没有可报告的种子覆盖收益。

本阶段把项目参数移入通用 JSON 配置，并完成了一个公开项目的原生编译、属性识别和三次 G0 基线。这说明接入工程有进展，但新项目端到端瓶颈尚未解决。建议选择 **B：只实现部分兼容，保留为可选实验**。现在不能把实验集作为论文正式实验集，也不应据此宣称 V2 在新项目上有效或无效。

## Origin Dollar：实际执行数据

### 原生编译、属性与静态分析

Origin Dollar Foundry 编译耗时约 4.18 秒，solc 为 0.8.28；Harness ABI 与字节码已保存。Echidna 2.3.2 识别原生 assertion 测试模式，最终复核的 Slither 分析耗时约 25.96 秒。Agent/API 阶段没有执行，因此没有生成耗时或成本数据。详细编译、属性与分析输出分别见 `结果/OriginDollar/03-Harness编译.json`、`02-echidna-official-config-preflight.log`、`04-slither-properties.json` 和 `04-slither.log`。

V2 静态上下文识别了 36 个 ABI 兼容候选动作，但余额、授权额度等状态写入点没有匹配出足够的状态依赖证据，`dependency_status=incomplete`。这不是完整通过分析门槛，也不能据此让 Agent 生成候选。

### Anvil 部署探针

补上通用 Solidity `Error(string)` 与 `Panic(uint256)` 解码、保留紧凑调用栈后，重新运行了编译、Slither、Anvil 探针和已有 G0 结果汇总。编译与属性识别再次通过，但部署收据仍为 `status=0`，Anvil trace 只返回 `execution reverted`，没有可解码的 revert 数据；完整机器结果见 `05-anvil-deploy-probe.json` 与 `phase29-result.json`。

失败原因可作有证据的源码推断：未修改的 `EchidnaSetup` 构造函数调用 `hevm.prank(ADDRESS_VAULT)` 后立即调用 `ousd.mint`；原始 OUSD 的 `mint` 带有 `onlyVault`。Foundry 文档把 `prank` 定义为改变下一次调用的 `msg.sender` 的 cheatcode；Anvil 文档描述的是本地 EVM 节点及其 impersonation 等 RPC 能力。[Foundry prank 说明](https://www.getfoundry.sh/reference/cheatcodes/prank)、[Anvil 说明](https://www.getfoundry.sh/anvil/index.html)。结合原 Harness 源码和部署 trace，普通 Anvil 上的 `hevm.prank` 没有 Foundry 测试运行器的调用者替换效果，因此后续 mint 很可能由 Harness 地址发出并触发权限回滚。trace 未返回可解码的具体失败帧，所以报告把这一原因标为源码推断。若要在不改 Harness 语义的前提下继续，需要提供等价的真实初始化部署环境；本阶段没有为此重写源码或继续修复。

### G0：Echidna 原生基线

三次运行使用同一个 Harness、属性集合和配置：workers=1、序列长度 8、testLimit=5000、每次 timeout=60 秒；外部语料为空。随机种子为 20261129、20261130、20261131。三次运行均完成，目标 assertion 测试均为 passing，没有目标反例。

| 重复 | Echidna 随机种子 | 实际调用数 | 最终 unique instructions | 所选函数覆盖 | 断言行 37 命中 |
|---|---:|---:|---:|---:|---:|
| 1 | 20261129 | 5001 | 14448 | 8/9 行 | 0 |
| 2 | 20261130 | 5001 | 14079 | 6/9 行 | 0 |
| 3 | 20261131 | 5000 | 14907 | 6/9 行 | 0 |

`testLimit=5000` 是明确的非零预算；日志中的调用计数是 Echidna 实际报告值，前两次为 5001，按原样保留。目标操作行覆盖来自每次运行的 LCOV，而不是把其他属性的结果折算为目标成功。每次原始日志和覆盖文件位于 `结果/OriginDollar/fuzz/G0/repeat-{1,2,3}/corpus/`；汇总见 `phase29-result.json` 和 `echidna-comparison.json`。

### G1/G2 与效果判断

V2 分析门槛未过，且 Anvil 部署探针未复核通过，因此没有 Agent 原始候选、没有同一候选的修复版本，也没有有效种子可以注入。G1、G2 均未运行。三个 G0 值只能描述原生基线在本预算下的随机波动，不能与种子组作收益比较。

所以本阶段的真实结果是：

1. 生成候选：无。
2. V2 候选交易真实执行：无。
3. 目标状态到达：无证据。
4. 种子被 Echidna/Medusa 回放：无。
5. 种子导致覆盖提升：未测量。
6. 目标属性反例：未发现；这不等于证明属性安全。
7. 规划与参数修复的相对贡献：无法归因。

Echidna Phase26 的历史固定案例曾报告种子收益；Phase28 的 BeeStorage 与 Immutable 历史种子曾通过 Medusa 回放。但本轮没有在新公开项目上取得对应 G1/G2 结果，故无法判断新项目方向是否一致。本轮没有对新项目运行 Medusa。

## 通用接入改动与验证范围

本轮增加 JSON 项目配置加载器，将来源版本、源码和 Harness 路径、编译器及 remappings、部署参数、sender/value、属性模式、Echidna/Medusa 设置和目标状态证据配置集中管理。现有 `PROJECTS` 项目表由旧静态配置与新配置合并，以保留旧项目入口；Origin Dollar 不需要修改真实 Solidity 业务代码或属性。新增 Phase29 驱动按八级记录状态并保存 G0 原始日志、LCOV 与机器汇总。Anvil 部署失败路径增加 trace/revert 信息采集。

Windows Python 的本机路径缺少项目依赖，但在仓库 Linux 环境完成了属性适配器测试、旧七项目与 Origin Dollar 上下文读取以及 Origin Dollar 编译/Slither/Anvil 复跑。属性适配器旧测试夹具少传了当前构造器要求的 `property_functions` 参数；同步测试调用签名后，12 项回归全部通过。另将七条既有 Phase25 种子回放写入 Phase29 独立目录，与历史状态逐条比较，7/7 的原始回放和依赖提示回放分类一致；没有覆盖历史结果文件。执行记录见[本地验证日志](../func/测试过程/SCFuzzBench公开项目接入/结果/12-static-and-compatibility-checks.log)。旧七个项目的静态属性上下文读取均通过；这不替代逐项目编译、Anvil 和 fuzz 运行时回归。

一次原计划调用 DeepSeek 生成 Agent 候选的操作被本机自动审批拦截：系统指出这会把项目源码、属性上下文和候选生成提示发送到外部 DeepSeek API；该次请求没有发出。该限制与当前 V2 依赖分析不完整是两个独立门槛，不能把未生成候选记录成算法失败。后续若要继续该路径，需要在获准的数据发送范围内执行。

## 研究问题回答与建议

1. **新项目接入瓶颈解决了吗？** 部分缓解了配置分散问题，已把一个新项目接入到编译、原生属性和初步 V2 分析；完整接入瓶颈还没有解决。
2. **哪些真实项目完整跑通？** 本阶段五个新候选中为零。Origin Dollar 最接近，但没有通过 V2 依赖分析和 Anvil 部署探针。
3. **V2 在新项目上取得实际提升了吗？** 没有可比较的种子组，不能说提升或退步。
4. **提升来自规划还是参数修复？** 无法判断；两种候选都没有进入执行。
5. **Echidna 和 Medusa 各自表现如何？** Origin Dollar 的 Echidna G0 原生基线可运行；没有新项目种子组。Medusa 只有 Phase28 的既有案例结果，本轮未扩展验证。
6. **实验集足以启动论文正式实验吗？** 不足。当前没有新公开项目完整端到端结果，也没有配对的 G0/G1/G2 数据。
7. **还缺什么？下一步冻结实验集吗？** 候选版本已经冻结，暂时不扩大候选池；还需解决依赖可复现获取、至少两个独立项目完成 V2 分析与 Anvil 初始化、固定候选通过回放，并拿到相同预算的三组对照。达到这些条件前，不建议冻结为论文正式实验集。
