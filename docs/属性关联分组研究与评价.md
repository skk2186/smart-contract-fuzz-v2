# 属性关联分组：真实项目观察与独立评价

## 目的与范围

分组用于复用属性上下文和**候选**交易前缀。每条 `echidna_*` 属性仍以原有 `property_id` 独立保留；分组不增删测试目标，也不将组内约束取并集替代各属性约束。本轮只使用现有属性分析 JSON 构建依赖图、分组和静态评价，未调用 Agent、生成种子或运行 Echidna。源码位置见 `func/属性关联分组.py`。

## 输入与复现

使用 Hokusai、Request Network 和 Immutable 项目原生显式属性的适配器输出。Hokusai 与 Immutable 的完整项目分析过程见[属性分析适配器使用说明](属性分析适配器使用说明.md)。Request 本轮使用 `sol/真实项目/Request/src/contracts/test/EchidnaERC20CommerceEscrowWrapper.sol`，Solidity 0.8.20，OpenZeppelin 4 导入映射；结果为 `complete`，共 16 条属性。以下命令在 V2 根目录、已安装的 Python 环境中执行：

```bash
SOLC_VERSION=0.8.20 python func/属性分析适配器.py \
  sol/真实项目/Request/src/contracts/test/EchidnaERC20CommerceEscrowWrapper.sol \
  --solc-remaps '@openzeppelin/contracts/=sol/真实项目/依赖/OpenZeppelin4/contracts/' \
  --output .tools/results/request-property.json

python func/测试属性关联分组.py
python func/属性关联分组.py \
  --input Hokusai=.tools/results/hokusai-full-final.json \
  --input Request=.tools/results/request-property.json \
  --input Immutable=.tools/results/immutable-full-final.json \
  --output .tools/results/属性关联分组.json
```

`--random-trials` 默认为 200，`--seed` 默认为 42。输出 JSON 对每个组保留成员及原属性身份、全组共享核心和逐对证据；`graph` 保留符合分组条件的边，`evaluation` 保留三种策略的比较。

## 共享关系与算法

从每条属性抽取三类信息：① 可写且被属性读取的状态，区分本合约状态与带静态接收者路径的外部状态；② 有写入效果证据的候选函数；③ 前置状态闭包中的候选准备函数。③ **不参与分组建图**，只用于留出式评价。不同分析合约及源码上下文之间禁止建边；即使状态变量定义相同，也不据此推断运行时合约实例相同。无法确认的实例别名候选不进入边证据，仍可在原始属性分析报告中查看。

同上下文两属性若共享至少一个可写状态及一个候选写入函数，或共享至少两个可写状态，即建立有证据的边。边权为 `2 × 共享状态数 + 共享候选函数数`，仅决定合并顺序。贪心合并要求新组内**每一对**都有边，并要求全组至少有一个共同状态。这样避免简单连通分量把仅通过中间属性相连的两端属性放进同组。逐对证据及全组共享核心都写入 JSON，供人工审核。静态接收者路径只是路径证据，不能保证部署后的别名关系，更不能证明函数序列可执行。

## 静态评价结果

随机基线在每个分析合约上下文内打乱属性，严格复用算法产出的组规模，进行 200 次；不会跨部署上下文随机拼组。独立基线每属性一个组。下表的“组内对”是组内不同属性对数量；“共享准备对”是两属性具有至少一个共同候选准备函数的组内对数量；“复用状态/函数”是每组成员特征总数减去去重后的特征数。随机值为 200 次均值。所有数值为本轮真实 JSON 运行结果，不是种子或漏洞检测指标。

| 项目 | 属性数 | 分组数 | 非单属性组数 | 多属性组成员 | 组内对：本方法 / 随机 | 共享准备对：本方法 / 随机 | 复用状态：本方法 / 随机 | 复用函数：本方法 / 随机 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Hokusai | 101 | 84 | 10 | 27 | 31 / 31 | 9 / 5.67 | 33 / 11.98 | 87 / 37.89 |
| Request Network | 16 | 10 | 2 | 8 | 13 / 13 | 0 / 0.32 | 7 / 1.65 | 16 / 7.35 |
| Immutable | 32 | 6 | 4 | 30 | 172 / 172 | 13 / 9.66 | 43 / 33.66 | 63 / 53.87 |

独立基线分别为 101、16、32 个单属性组，所有组内共享量均为 0。三项目共 149 条属性，输出中仍有 149 个不同 `property_id`，每个恰好出现一次。算法组内的“有证据对”必然较高，因为建组就依赖这些边；不能将这一项当作独立效果证明。前置准备信息虽未用于建图，但仍来自同一静态分析器，不是可执行性真值。Request 的留出指标甚至低于随机均值，应如实保留。

## 人工审核

| 项目与实例 | 组内关系判断 | 边界 |
| --- | --- | --- |
| Hokusai：`EchidnaAMMGraduation` 的供应赎回、受害者赎回、储备属性 | 共同观察同一静态 `amm` 接收者路径下的 `reserveBalance`，候选含 `buy`、`sell`、`depositOwnFees`。复用 AMM 状态和交易候选上下文有依据。 | 尚不能断言一条具体买卖前缀同时满足三条属性的参数和权限条件。 |
| Hokusai：`EchidnaRewardVestingVault` 的 4 条归属/领取属性 | 共同观察 `vault.schedules` 和 `scheduleIds`，共享 `createSchedule`、`claim`；留出的共同准备动作包括 `createSchedule`。这是较明确的准备操作复用候选。 | 尚需实际执行验证领取者与时间条件。 |
| Request：余额/代币守恒等 5 条属性 | 共同观察 `token._balances`，共享授权、扣款、退款驱动函数。支付流上下文可以一起提供。 | 部分属性实际关心不同账户余额；不能把它们当作同一断言。 |
| Request：支付计数器相关的 3 条属性 | 共同 `paymentRefCounter` 和授权/扣款候选函数，静态关联成立。 | `echidna_payment_ref_counter_monotonic()` 的 `uint256 >= 0` 恒真；该组三属性的安全价值不能仅凭共享关系判断。 |
| Immutable：转移相关的 5 条属性 | 共同观察 `owners`、`tokenOwners`，且共享 `transferFrom`、`safeTransferFrom` 等动作；共同准备动作涉及授权与转移。 | 具体调用者、授权、接收者回调仍可能分叉。 |
| Immutable：18 条属性的大组 | 全组共享 `totalMinted` 和 `mintForTest`，从“共同铸造上下文”看有静态证据。 | 组内混合边界铸造、回调、销毁不存在代币等不同约束；共享函数并不等于共享有效前缀。这个大组显示通用计数器会造成过宽聚合，后续应检验上下文成本或增加保守拆分依据。 |

Immutable 的部分 `echidna_*` 属性本身调用会修改状态的函数；Request 的若干属性包含宽松的 `catch { return true; }`。这些是测试目标质量与执行语义问题，本轮没有修改项目源码或筛选掉它们。未来报告漏洞发现效率时须单独审查，不能把静态分组好看等同于属性质量高。

## 结论边界

真实报告中存在可复用的状态、候选写入函数和少量共同准备动作，足以支持构建可解释的**候选共享上下文**。当前结果不证明共享交易前缀可执行，也不证明 Token、有效种子或反例发现收益。尤其是 Immutable 大组和 Request 恒真属性说明需要后续逐属性保留约束、执行验证和按完整预算比较；分组不能改变最终测试的 149 条属性。
