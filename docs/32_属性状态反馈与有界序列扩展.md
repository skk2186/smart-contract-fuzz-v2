## 1. 结论摘要

本阶段在 Phase30B 冻结的 Agent A/B 候选 deposit(0) → withdraw(0, 1 ETH) 上，加入预算受限的序列扩展模块。模块依据 Anvil 逐笔执行、属性 getter、调用 trace 和余额变化，决定是否补步骤、重复已有操作或改变 ABI 角色参数。没有调用新 Agent；Phase30B 人工 Oracle 没有作为输入、模板、种子或 Echidna 语料。

模块在 10 次扩展候选执行内生成四笔序列：

    deposit(account=0, value=1 ETH)
    → refund(account=0)
    → deposit(account=1, value=1 ETH)
    → withdraw(account=0, amount=1 ETH)

Wallet 原始业务源码、Harness 和属性均未修改。Anvil 四笔均成功；第 4 笔后 actor 0 累计提款 2 ETH、累计存款 1 ETH，属性变假。Echidna 2.3.2 在三个冻结随机种子的 seed-only 回放中均重现该属性反例。这是自动生成且经另一执行引擎重放确认的 Wallet 机制正向结果；不是未知漏洞发现，也不是独立留出样本结论。

E3 的 testLimit=500 运行在种子重放时立即触发属性反例，随后仅记录 5 次总调用便停止，没有完成 500 预算；E3 后续 fuzz 新增 LCOV 行数为 0。四个预冻结独立项目都没有通过接入门，没有独立样本对照。当前证据不支持覆盖收益、跨项目泛化或新颖性主张。

## 3. 冻结条件和实现

方案在 Phase31 编译、Agent 结果、Anvil 执行和 Echidna 结果之前冻结于 00-Phase31实验方案冻结.json，SHA-256 为 3344289a8f408de863b1e754bebf90091f4e98839b75e2b9763879e7c153201b。

| 项目 | 冻结值 |
|---|---|
| 合约、Harness、属性 | Phase30A SmartBugs Wallet；保持原样；属性 WalletHarness.echidna_wallet_accounting_respected() |
| A/B 输入 | 原样复用 Phase30B P1；Phase31 新 Agent 调用为 0 |
| 序列长度 / 保留前缀 | 最大 8 / 最多 4 个多样前缀 |
| 候选预算 | 每属性、每模式最多 24 次候选 Anvil 执行；每候选至多一次现有参数修复 |
| 初始余额 | 每个测试账户 100 ETH |
| Echidna | 2.3.2；种子 20261125、20261135、20261145；testLimit=0 与 500；单 worker、长度 8、stopOnFail=false、禁用 Slither、60 秒 |
| Oracle 隔离 | 不进入 Agent、扩展模板、候选语料或 Echidna；机器结果记录 manual_oracle_read=false、manual_oracle_used=false |

新增通用模块 [状态反馈序列扩展.py](../func/功能/状态反馈序列扩展.py)。模块不按函数名称判断业务语义，名称只用于匹配 ABI。候选通过 ABI 参数数量和类型检查，并需要属性动作、静态读写、角色或真实执行反馈之一作为证据；每个候选都重新部署并由 Anvil 回放。

模块目前支持三类操作：一是按属性动作的静态读写证据插入已有动作并保留已成功前缀；二是仅重复曾成功且改变属性 getter/跟踪状态、同时具有存储或余额影响的交易；三是 trace 证明同一合约地址被调用、观察到正向资源变化且依赖调用失败后，基于 ABI 角色参数或发送者池生成变体。所有新候选继续受 ABI 检查和 Anvil 验证约束。

反馈向量包括交易成功、属性相关 getter 变化、相关状态新颖性、后续依赖证据、可解析数值不变量的归一化距离及实际反例。无法可靠解析的属性不计算目标距离，退化为状态新颖性、依赖证据和执行成功性。保留策略在至多四个前缀中兼顾执行结果、角色、序列形状与状态变化，避免只留当前距离最小的路径。

修改 [种子验证.py](../func/功能/种子验证.py)：逐笔记录调用 trace 的 value、余额前后变化、changed_predicate_getters 和 property_related_state_changed。Echidna 解析器不再把 tests:x/y 或 fuzzing:n/500 当作测试用例数，也固定将 mutation_evidence 记为 false，因为这些进度文字不能证明新变异序列。

新增驱动 [Phase31状态反馈序列扩展.py](../func/测试过程/SCFuzzBench公开项目接入/Phase31状态反馈序列扩展.py) 和 [Phase31非Wallet回归.py](../func/测试过程/SCFuzzBench公开项目接入/Phase31非Wallet回归.py)。后者在 PaperExample 做人工静态依赖夹具，只确认通用插入机制可运行，不作为自动发现或独立样本结果。Agent A/B、原参数修复和 Echidna 主引擎均保留。E2 没有修复提案，所以 E2 与 E1 候选完全相同；扩展器不替代参数修复。

## 4. Wallet 回归、根因及逐笔反例

### 4.1 Phase30B 原规划缺口

Phase30B P1 是 deposit(0) → withdraw(0, 1 ETH)，P0 是 deposit(0) → refund(0)。两条都只有 actor 0 的动作，没有第二个 Harness 账户提供共享资金。

| 环节 | 已核实证据 | 结论范围 |
|---|---|---|
| Slither | 04-slither-property-analysis.json 的 cross_contract.observations、balance_observations、prerequisite_state_closure 均为空，并将外部调用/别名列为未知。 | 已证实静态输出缺少跨 Wallet 调用与共享池依赖闭包；单独不能证明 Agent 的内部推理。 |
| Agent A | 冻结 P0/P1 输出各只有两步，账户索引均为 0；没有 actor1 注资及 actor0 后续提款。 | 已证实输出遗漏；没有思维链或单变量实验确定唯一内部原因。“共享池/跨 actor 表示不足”仍是有支持的解释，不是唯一因果结论。 |
| Agent B/参数修复 | P1 完整执行成功，参数修复没有提案；Phase31 E2 与 E1 fingerprint 完全相同。接口只改参数，不会插入交易步骤。 | 已证实参数修复不能填补缺失动作。 |
| 执行反馈 | Phase30B 已记录属性 getter，因此“回放完全没有 getter”不成立。旧流程没有将逐笔反馈送入序列扩展闭环；Phase31 才连接 getter 差分、共享资源 trace 和失败执行。 | 已证实反馈流程差别；原 getter 是否进 Agent A 初始提示，证据不足，不能断言没有提供。 |
| 环境 | Phase30A RPC 余额问题由 Phase30B/31 每账户 100 ETH 排除；P1 在该余额下完整执行但未达标。 | 不是缺少序列步骤的原因。 |
| Echidna 统计 | Phase30A tests: 0/1 是一项属性未失败，不是 fuzz case 数；Sequence replayed 只说明语料回放。 | mutation_evidence=true 无法由该日志推出。本轮使用 LCOV 差集，不将进度分母解释为 case 数。 |

因此，已确认的是静态上下文缺跨合约/共享余额关系、A/B 候选没有跨 actor 资金操作、参数修复只能改参数，以及旧执行反馈没有驱动扩展。内部模型为何没有提出特定序列，仍不能唯一归因。

### 4.2 自动生成的逐笔 Anvil 轨迹

原始记录为 Wallet机制回归/attempt-02-feedback-priority/E3-扩展回放.json。候选 #10 的扩展类型为 shared_resource_role_expansion。每笔交易外部 sender 相同；account=0、account=1 经 Harness 映射到两个不同 WalletUser/actor。表中 Wallet 内部余额映射是由原始源码推导，并非直接 getter；其它数值来自每笔 getter 与余额 trace。

| 步骤 | 调用 | Anvil 状态 | Wallet 池余额 | 累计存款 actor0 / actor1 | 累计提款 actor0 / actor1 | 属性 |
|---|---|---|---:|---:|---:|---|
| 初始 | — | — | 0 ETH | 0 / 0 ETH | 0 / 0 ETH | 真 |
| 1 | actor0 deposit 1 ETH | 成功 | 0→1 ETH | 1 / 0 ETH | 0 / 0 ETH | 真 |
| 2 | actor0 refund | 成功 | 1→0 ETH | 1 / 0 ETH | 1 / 0 ETH | 真 |
| 3 | actor1 deposit 1 ETH | 成功 | 0→1 ETH | 1 / 1 ETH | 1 / 0 ETH | 真 |
| 4 | actor0 withdraw 1 ETH | 成功 | 1→0 ETH | 1 / 1 ETH | 2 / 0 ETH | **假** |

原始 Wallet.refund() 将 actor0 对应 WalletUser 的 1 ETH 转出，但没有清零 Wallet 内部余额映射。之后 actor1 向同一个 Wallet 合约注入 1 ETH 共享资金，actor0 再按未清除的 1 ETH 记账提款。故 actor0 累计提款为 2 ETH，累计存款为 1 ETH。该解释由原始代码、调用 trace、池余额和逐笔 getter 共同支持。

候选 #10 的提案证据是：同一 trace 地址出现正向资源变化，依赖操作失败，于是改变角色值后在失败调用前尝试新前置步骤。没有向扩展器提供人工 Oracle。E3 共执行 10 个扩展候选、加一次基线 Anvil 回放，共 11 次，耗时 8.012526 秒，Agent/API 调用和 Token 为 0。反例 fingerprint 为 e24710d808cfea34ac5438fcdd925b69f5a4b4906833c831a10fa4f3cddcc2f3。

### 4.3 非 Wallet 回归

PaperExample 源码不变。人工夹具提供的依赖关系是 set0 写 flag0、set1 读 flag0 并写 flag1，属性读取 flag1。模块将 set0(23) 扩展为 set0(23) → set1(5)，两笔 Anvil 均成功，echidna_flag() 从真变假。该结果明确标记为 manual non-Wallet regression fixture，因为关系由测试夹具指定；它只说明模块不依赖 Wallet 结构，不计自动发现、独立验证或覆盖收益。

## 7. 证据判断与下一步

可用于论文内部机制论证的真实证据：冻结 A/B 输入下模块自主生成与人工 Oracle 不同的 4 步序列；Anvil 第 4 笔后目标属性为假；账户 getter 与 Wallet 共享池轨迹一致；Echidna 三个随机种子均回放同一反例。PaperExample 只作为人工关系回归夹具。

负面结果同时保留：E3 未完成 500 预算且 fuzz 新增覆盖为 0；随机扩展没到达目标，且覆盖增量与 E1/E2 一样；静态扩展没有合格种子；首次随机/静态组输入误接，12 次运行被排除；四个独立项目没有任何正式运行。因而尚未在两个独立样本观察到同向收益，也尚未获得可支持论文结论的独立项目证据。已引用研究也表明序列依赖和反馈扩展已有先例，不能将当前实现描述为已证明的新算法。

下一阶段建议先建立具有原生可运行属性和可离线复现依赖的独立样本池，再开展至少两个独立样本的冻结配对试验。只有两个样本呈方向一致的收益、计入种子准备成本后仍然成立，才考虑扩展到 20–30 个样本。本阶段在代码及报告完成后停止，不自动进入下一阶段。
