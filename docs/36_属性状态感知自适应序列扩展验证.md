# Phase36：属性状态感知的自适应序列扩展验证

更新时间：2026-11-20。仓库：`smart-contract-fuzz-v2`。本报告验证一项有限假设：扩展前使用已有执行状态和属性依赖证据，能否减少低价值 E3 回放，同时保留 Wallet 已知反例的发现能力。它是开发集机制诊断，不是独立真实项目泛化实验。

## 1. 研究问题与冻结条件

实验开始前重新核验 `main`：本地 HEAD 与 GitHub 只读接口返回的远程 HEAD 均为 `963afe101d4c0ef02db5af6ea21b138f49e29c73`。Phase35 冻结文件仍记录其更早的远程 HEAD `dded14f`；Phase36 冻结文件已写入更正值和查询来源。实验前跟踪文件无改动；DODO、Strata、VeryLiquidVaults、eBTC 四个已有未跟踪项目目录原样保留。

阶段冻结文件为 [`00-Phase36冻结.json`](../func/测试过程/跨交易属性状态依赖审计/结果/Phase36-20261120/00-Phase36冻结.json)。其中冻结 Phase35 的 E2 序列、核心算法 SHA-256、Phase36 门控及驱动哈希，以及最大序列长度 8、每个扩展方法 24 个候选预算、最多保留 4 个前缀、扩展随机种子基数 `20261120`。G1 使用原 E3 候选生成和 Anvil 回放；G2 只在同一候选生成与回放之间增加门控；G0 只回放 E2 基线。每个组均重新部署，基线回放计入总 Anvil 回放和实测时间。

五个主场景的 G0/G1/G2 均使用同一 E2 输入指纹。B/C/D 沿用 Phase35 每类一次的 Agent A/B 输入，本轮 Agent 调用数为 0；不改提示词、参数修复、E3 核心实现或 Echidna 逻辑。没有运行模糊测试 campaign。删步安全输入只从独立 Oracle 序列中删除指定的一笔交易后写入冻结文件；正式运行只读取删减序列，不读取完整 Oracle 序列。

## 2. 门控规则

独立实验模块见 [`Phase36属性状态感知门控.py`](../func/测试过程/跨交易属性状态依赖审计/Phase36属性状态感知门控.py)，配对驱动见 [`Phase36自适应扩展.py`](../func/测试过程/跨交易属性状态依赖审计/Phase36自适应扩展.py)。门控不修改 E3 候选生成器，也不按合约名、项目名、Oracle 答案或实验组最终成绩决策。

决策规则在 Anvil 候选回放前执行：

1. 父序列未完整成功、存在未解析观察，或候选不是已支持的重复类型时，决策为“未知/扩展”，保留候选。
2. 对重复候选，若父状态中的已观测 getter 与同一动作的 Slither 简单守卫直接矛盾，例如 `stage()==3` 而重复动作要求 `stage==1`，则跳过该候选并保存守卫及状态证据。这个判断仅证明该候选从当前父状态回放会回退，不推断任务或属性已经完成。
3. 对源代码显式表达 `sum(balanceOf(...)) == totalSupply()` 的供给守恒属性，首次重复仍作为探测执行。只有所有相关 getter 均已观测、探测前后的守恒残差相同、余额与供给的实测增量相等，且最大长度下的累计值仍低于 `uint256` 上限时，才跳过后续完全相同的重复候选。
4. 其他关系、未知 mapping、可能的角色/资源/数值依赖均保留扩展。被跳过候选计入候选考虑预算，不把跳过计为成功。

这一实现只覆盖可解释的简单状态相等守卫和供给守恒关系；未知默认保留，因此它不能识别一般化的任意属性目标距离或解决 E3 原有依赖缺口。

## 3. 主场景 G0/G1/G2 对照

下表时间为五个场景各自一次真实配对运行的完整扩展阶段耗时，包含基线回放和 G2 门控；“候选回放”不含基线，Anvil 总回放包含基线。

| 场景 | G0：候选回放 / Anvil 总回放 / 秒 | G1：候选回放 / Anvil 总回放 / 秒 | G2：考虑 / 候选回放 / 跳过 / Anvil 总回放 / 秒 | 冻结目标及结果 |
|---|---:|---:|---:|---|
| A Wallet02Refund | 0 / 1 / 0.517 | 10 / 11 / 5.894 | 10 / 10 / 0 / 11 / 5.892；门控 0.000240 秒 | G2 与 G1 均在候选 10 找到属性反例。 |
| B 普通状态机 | 0 / 1 / 0.437 | 24 / 25 / 10.815 | 3 / 0 / 3 / 1 / 0.467；门控 0.000222 秒 | E2 已到达 stage 3；G1 的 24 个候选完整回放全失败，G2 在第一层按三个 stage 守卫跳过必回退的重复。 |
| C 纯 `msg.sender` 跨账户 | 0 / 1 / 0.423 | 0 / 1 / 0.447 | 0 / 0 / 0 / 1 / 0.462 | E2 基线可回放；原 E3 无候选，G2 没有节省空间。 |
| D ERC20 allowance | 0 / 1 / 0.511 | 5 / 6 / 4.050 | 5 / 5 / 0 / 6 / 4.473；门控 0.000143 秒 | E1/E2 已由既有独立 getter 核验到达委托消费状态；属性 mapping 观察不完整，G2 保留所有重复 mint。没有新增授权/消费状态。 |
| E Pigfox RWA 供给守恒 | 0 / 1 / 0.959 | 7 / 8 / 97.845 | 2 / 1 / 1 / 2 / 3.378；门控 0.000059 秒 | E2 已满足守恒属性，G1 的 7 个重复 mint 均只同步增加余额和供给；G2 探测 1 次后跳过 1 个相同重复。 |

五个主场景合计：G0 为 5 次基线回放、2.848 秒；G1 为 46 次候选回放、51 次 Anvil 总回放、119.051 秒；G2 为 20 个候选考虑、16 次候选回放、4 项跳过、21 次总回放、14.672 秒，门控累计 0.000664 秒。G2 比 G1 少 30 次候选回放（65.2%），观察到的扩展阶段时间少 104.379 秒（87.7%）。单次运行不能把全部时间差都归因于门控；E 组占 G1 的大部分耗时，因此候选数是更稳健的效率证据。

### 按目标进展而非 getter 变化计数

G1 的旧汇总器把 Pigfox 每次 `property_related_state_changed` 记作目标到达，故原始 `frozen_goal_sequences` 为 7；这个字段只代表属性 getter 有变化，不代表目标关系改善。Phase36 根据冻结属性的实际等式计算 `sum(balanceOf) - totalSupply`：E2 基线残差为 0；G1 七个候选和 G2 的一个探测候选残差仍全为 0，目标进展均为 0。Pigfox 的 getter 变化被保留为原始证据，但没有包装成算法收益。

Wallet 的 G2 候选 10 序列为：`deposit(0) → refund(0) → deposit(1) → withdraw(0,1 ETH)`。四笔均成功；前三笔后属性为真，最后 `cumulativePayout(0)` 从 1 ETH 增至 2 ETH，属性变为 false。G1/G2 的 Anvil 轨迹完全一致，G2 没有过滤 Wallet 的静态插入、资源角色候选或此前尚未证明低价值的重复。

Echidna 首次 seed-only 命令虽然退出码为 0，但日志显示加载 0 条序列。该次被标记为无效复核并原样保留；依据 Phase35 已记录的通用 corpusDir 修复，只把同一 seed 所在 `corpus-input` 目录传给 Echidna，再执行一次。修复后加载 1 条、重放 1 条，且 Echidna 报告 `echidna_wallet_accounting_respected` 失败，与 Anvil 的反例一致；`test_limit=0`，没有启动 fuzz。首次与修复后日志分别见 [首轮日志](../func/测试过程/跨交易属性状态依赖审计/结果/Phase36-20261120/Echidna-seed-only/Wallet02Refund/G2/run/echidna.log)和[修复后日志](../func/测试过程/跨交易属性状态依赖审计/结果/Phase36-20261120/Echidna-seed-only/Wallet02Refund/G2-corpusDir-fix/corpus-input/echidna.log)。

## 4. 缺失前置步骤安全性

冻结输入分别从 B 删除 `configureTask`、从 C 删除 `authorizeOperator`、从 D 删除 `approve`。G1/G2 各自从同一删减序列开始。G2 没有跳过任何候选：三个场景的父序列均有交易回退，门控按未知默认保留。结果如下：

| 场景 | 初始回放 | G1/G2 候选回放 | 有效完整序列 | 观察到的 E3 限制 |
|---|---|---:|---:|---|
| B 删除 configure | `createTask` 成功，`executeTask` 回退 | 各 24 | 0 | E3 确实插入 `configureTask(1)`，但随后 `executeTask(3)` 因 `LIMIT_EXCEEDED` 回退；未推导满足 amount=3 所需的 limit。 |
| C 删除 authorize | `fundCredit` 成功，`executeFor` 回退 | 各 2 | 0 | 插入的授权把 owner 地址授权给 owner，而消费者 sender 是 operator；回退原因为 `NOT_AUTHORIZED_OPERATOR`。 |
| D 删除 approve | `mint` 成功，`transferFrom` 回退 | 各 24 | 0 | 插入的 `approve` 授权给 owner 地址，而执行者是 spender；回退原因为 `ALLOWANCE_TOO_LOW`。 |

这三项结果分别是“门控正确保留，但 E3 参数/角色补全失败”，不是门控误跳过。删步输入与每笔候选轨迹见 [`00-缺失前置步骤删减输入.json`](../func/测试过程/跨交易属性状态依赖审计/结果/Phase36-20261120/00-缺失前置步骤删减输入.json)及 [`SafetyMissingPrerequisite`](../func/测试过程/跨交易属性状态依赖审计/结果/Phase36-20261120/SafetyMissingPrerequisite/)。D 删步的 G2 观察到单候选最长 35.745 秒，整组 75.162 秒，而同预算 G1 为 9.478 秒；两组均执行 24 候选、门控没有跳过。该单次候选级延迟不归因于门控，也没有为追求配对时间而重跑。

## 5. 失败与能力边界

- G2 没有减少 A 的候选，保留 Wallet 成功结果的直接代价是与 G1 相同的 10 次候选回放。
- C 主任务没有 E3 候选；自适应门控无法补出 E3 本来没有生成的动作。
- D 主任务的 `delegatedSpent` 等 mapping getter 未解析；由于不能确认重复 mint 与目标消费状态无关，门控没有跳过候选。这是保守行为，也说明现有观测不足以提供 D 的效率收益。
- B/C/D 删步任务都出现了正确的插入动作，但参数/角色值不满足消费者守卫；E3 不能从当前反馈补出正确 limit、授权 operator 或 allowance spender。
- Pigfox 仅证明一个特定显式供给守恒等式可由完整 getter 快照和一次探测判定。不能据此声称门控能识别任意累积边界或一般属性进展。
- Echidna 首轮无 seed 加载，不能计作验证；修复后同一 seed 加载并重放，才计入 Wallet 复核。没有覆盖 campaign 数据。

完整门控决策与执行反馈联表为 [`Phase36-诊断细项.json`](../func/测试过程/跨交易属性状态依赖审计/结果/Phase36-20261120/Phase36-诊断细项.json)；所有 G0/G1/G2 原始 Anvil 回放、逐候选门控 JSON 和 Wallet 两次 Echidna 日志均保存在 [`结果/Phase36-20261120`](../func/测试过程/跨交易属性状态依赖审计/结果/Phase36-20261120/)。

## 6. 结论与阶段门

按预先给定的验收条件，开发集最小验证达到门槛：Wallet 的 Anvil/Echidna 反例仍被发现；B 和 Pigfox 两个原有无效扩展场景的候选回放分别减少 100% 和 85.7%；基线有效种子保留；三种删步诊断均没有被门控误跳过；主实验 G2 的实测总耗时包含门控并低于 G1。故本轮选择 **A：开发集机制验证达到预设门槛，可以冻结后进行独立验证**。

这里的 A 只授权将本轮门控规则和实现哈希冻结为一个待独立验证的候选版本，不表示机制已证明跨项目泛化。核心 E3 对缺失额度、msg.sender 授权对象和 ERC20 spender 绑定的依赖识别缺口仍在。没有启动下一阶段、扩大样本、修改算法或推送 Git。
