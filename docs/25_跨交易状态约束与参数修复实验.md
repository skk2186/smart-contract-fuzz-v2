# Phase 25：跨交易状态约束与参数修复实验

日期：2026-11-17

## 结论

- 新增的通用回放约束处理，在四个不同项目的无提示失败样本上都带来可重复的 Anvil 目标操作成功：Request 退款、Immutable mint 后 approve、BeeStorage 创建批次后 topUp、OpenNFTs mint 后转给目标地址均为 G1 3/3；对应 G0 与关闭新机制的 G2 为 0/3。
- 机制复用了真实前序事件、公开 getter、内部调用 trace、状态差异和 Slither 静态守卫。Immutable、BeeStorage、OpenNFTs 通过唯一前序事件值绑定对象 ID；Request 根据 getter 观察到的退款额度和 Slither 中的零基索引关系，把退款引用从第一条支付改为第二条支付。每次参数修复都从部署状态完整重放；已成功的前序交易保留。
- BeeStorage 的原显式依赖提示兼容回归中，G0、G2 各 3/3；G1 2/3，剩余一条是 Anvil RPC 502 传输错误，非合约回滚。错误未删除，也未用重试结果替换。
- 四项 Anvil 成功样本均产生可用的 Echidna 种子。相同 500-testLimit 的配对运行中，种子组平均 unique instructions 和最终 LCOV 行数均高于 native；Request、Immutable、BeeStorage 的目标操作函数 LCOV 行命中均值也提高。OpenNFTs 的目标函数命中相同，且 3 次 Echidna 运行的 echidna_balance 均为 passing，尽管 Anvil 确认目标地址余额已达成。最终 LCOV 包含纯回放与后续变异，无法精确拆分两者的新增行数。
- **建议继续保留这项机制作为工程原型和可检验的研究假设；现有结果还不足以把它表述为已验证的论文创新。** 四个固定诊断样本不是独立留出基准；Echidna 增益幅度有限，OpenNFTs 的 Anvil 与 Echidna 属性结果也不一致。当前阶段未调用 DeepSeek API，未增加 Agent，未改动任何真实项目 Solidity 源码或属性。

## 实现

新增[跨交易状态约束处理器](../func/功能/跨交易状态约束.py)，修改[Anvil 种子验证器](../func/功能/种子验证.py)和[Agent 种子主流程](../deepseek/实验过程/运行Agent种子流程.py)。

1. **对象依赖。** 对后续 ABI 参数名作通用语义识别（如 id、key、reference、hash、nonce），只在前序事件中存在唯一、ABI 可编码的同名字段时绑定。绑定记录保留来源交易、事件、事件地址和字段；值不唯一或类型不兼容时不猜测。
2. **数值依赖。** 失败时解码内部 revert 文本；结合 Slither 的守卫/状态证据、操作源码片段和逐事件键的 getter 输出，识别参数与额度的语义关系。对于 1 + (index % counter) 这类源码映射，按事件顺序观察到的 getter 值选择可满足已观察额度的对象；若对应额度低于当前数值参数，也提出额度上界修复。逻辑不依赖项目名、函数名或特定金额常数。
3. **闭环验证。** 每条失败序列最多自动提出并应用一轮约束修复；只替换受影响交易参数，保留之前的交易和顺序，然后从干净部署状态重放完整序列。未通过重新执行的修复不能标记成功。之后仍受原有 Agent B 有界执行反馈次数限制。
4. **状态证据。** 回放记录增加匹配事件键的参数化 getter 结果、view 状态差异和完整但限长的 callTracer 内部调用轨迹。初始状态、交易后属性值、存储槽差异与内部错误分类继续按既有验证器口径记录。

**本批 Request 修复没有改 refundAmount。** 失败参数是 paymentIndex=0、refundAmount=1e18；getter 显示第一条引用的 refundableAmount=0、第二条引用为 1e18。静态源码关系与事件顺序共同支持将 paymentIndex 改为 1，原金额恰好等于被选引用的 getter 额度，完整重放后退款成功。因此本例实证的是“对象选择与数值额度匹配”闭环；金额下调分支已实现，但本轮没有构造出一个需要下调金额的运行样本，不将其单独宣称为实证能力。

### 逐笔修复证据

- **Request：** 原退款交易的 paymentIndex 从 0 改为 1，refundAmount 保持 1e18。PaymentAuthorized/CommercePaymentAuthorized 与 PaymentCharged 事件分别提供两个引用；对两个唯一引用执行的 getPaymentState(bytes8) 分别返回 refundableAmount=0 和 1e18。Slither 源码显示引用为 1 + (paymentIndex % paymentRefCounter)。修复后在全序列重放中退款操作成功，内部错误为 0。
- **Immutable：** mint 的 Transfer 事件 tokenId 被绑定到后续 approve 的 ABI tokenId，记录从原值 0 改为事件中的 340282366920938463463374607431768211968。approve 全序列重放成功，内部错误为 0。
- **BeeStorage 无提示样本：** BatchCreated.batchId 被绑定到 topUp 的 batchId，从历史猜测值 0x…01 改为真实事件值 0x23d7…15af9；topUp 成功。G0/G2 保留原错误值并各 3 次内部回滚。
- **OpenNFTs：** mint 的 Transfer.tokenID 值绑定到 transferFrom；to 地址根据属性源码设为 _other = address(1)。G1 三次目标交易成功，Anvil 在每次操作后观察到 echidna_balance() 为 false，即余额目标状态可达；G0/G2 未成功执行目标操作。
- **显式提示兼容：** 既有 batchId 提示在 G0/G2 全部成功；G1 一次传输层错误、两次成功，未出现状态依赖行为回退的内部证据。

## 验收判断与边界

1. **新方法多解决了什么？** 能从此前成功交易生成的事件值推断唯一对象 ID；能在同一参数对应多个对象时，结合所有对象的 getter 状态和 Slither 源码映射选择可满足约束的对象；失败后只改相关参数并验证完整序列。G0/G2 的 Request、Immutable、BeeStorage 无提示与 OpenNFTs 样本均不能完成目标操作，G1 分别 3/3 完成。
2. **Request、Immutable 是否从失败变成功？** 是。Request 的失败 refund 从错误引用切到可退款引用；Immutable approve 从不存在的 tokenId 切到 mint 返回事件中的 tokenId。两项 G1 均 3/3，而 G0/G2 均 0/3。Request 本轮未实证单独把过大的金额下调到额度这条分支。
3. **BeeStorage 是否保持？** 无提示 batchId 自动绑定 3/3；显式旧提示仍可用，G0/G2 3/3、G1 2/3。G1 唯一失败可追溯到 HTTP 502，计入失败和均值。
4. **是否跨项目复用？** 事件字段自动绑定覆盖 ERC-721 tokenId、BeeStorage batchId、OpenNFT tokenID；Request 另结合公开退款 getter、Slither 索引表达式和事件顺序。实现未按项目/函数分支。四个具体样本仍属于诊断/回归，而非论文留出基准。
5. **G1 是否优于 G0/G2、开销如何？** G1 在四个无提示任务的 Anvil 目标执行均为 3/3；G0/G2 均为 0/3。对应种子 Echidna 均值在四项目都提高 unique instructions/LCOV，但 OpenNFTs 目标函数覆盖不变、Echidna 属性不违反。Request 和 Immutable 的 Anvil 平均时间约增加 2.19 秒和 1.77 秒（含失败诊断、getter 观察及重新完整部署/执行）；BeeStorage 和 OpenNFTs 分别增加约 0.013 秒和 0.048 秒。回放过程无 API 费用；正式 Echidna 运行时长见上表。对离线种子验证而言绝对延迟可接受，但需要在更大样本验证吞吐影响。
6. **是否值得作为论文创新继续？** 继续保留为通用原型值得；单凭此阶段不足以宣称论文级创新。用户设定的停止条件（效果只在 BeeStorage 出现，或其他项目没有重复的目标状态到达收益）未触发：Request、Immutable、OpenNFTs 都有 3/3 的跨交易目标到达且 G0/G2 为 0/3。下一次研究性评估应采用事先冻结的留出项目/属性，并单独测量直接金额上界修复及 Echidna 纯回放/变异覆盖差；本阶段不据此追加定向调参。
