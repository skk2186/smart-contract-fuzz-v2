# 12 逐属性种子与原生 Echidna 对照阶段报告

日期：2026-11-14

## 阶段结论

V2 主流程现按“Slither 属性上下文 → 单属性 Agent A 交易计划 → Agent B 参数与发送者具体化 → Anvil 回放及有限反馈修复 → Echidna 语料注入”运行。主入口不再读取属性关联分组，也不再应用共享前缀；既有分组代码和历史实验结果保留。

本轮固定 3 条不同类型的真实属性。Agent A 为 3/3 条产生计划，Agent B 为 3/3 条返回具体交易；其中 2/3 通过 Anvil，成功率 66.7%。这两条 EVM 有效种子均在各自隔离的 V2 目录中被 Echidna 指定文件加载、回放，并观察到后续变异。第三条 NFT 序列两次 Anvil 回放都在 `approve` 阶段因 token 不存在而回滚；它仅作为单独的 Echidna-only 诊断语料验证，未计入 V2 主对照。

在同一 `testLimit=80` 下，两条有效种子带来的属性级覆盖增量为 +12,981 和 +4,777 条 unique instructions；未通过 Anvil 的 Immutable 属性增量为 0。三条合计 +17,758。按每条属性 60 秒端到端预算比较，合计只多 5 条（Immutable 0、Request 0、BeeStorage +5），V2 没有显示有实际意义的时间预算优势。两种预算下，Baseline 和 V2 均未发现目标属性违反（0/3）。当前证据支持“在相同 Echidna 测试上限下，已验证种子可以提升部分属性的覆盖”，不支持“包含生成时间后整体优于原生 Echidna”。

## 流程调整

- 主入口按属性分别请求 Agent A，提示中携带 Slither 读取状态、写入状态、前置状态闭包、候选动作效果和源码证据；共享前缀关闭。属性没有计划时允许一次带反馈的规划修正，失败仍保留在结果中。
- Agent B 明确负责 ABI 参数、发送者以及交易间的身份、对象 ID 和提交/揭示数据一致性。Anvil 回放失败后默认允许一次参数、发送者或时间反馈修复；每次回放和每次 API 请求都单独记录。
- 只有 Anvil 成功回放的语料标记为 `evm_valid` 并进入 V2 主比较。模型生成但未通过 Anvil 的交易只标记为 `echidna_only_diagnostic_candidate`，放在独立目录，不能计为 EVM 有效种子或混入主比较。
- 种子名使用全局 UUID；每个属性、方法和预算使用独立 Echidna 目录。Baseline 的初始 `coverage` 目录为空。V2 结果核对了目标种子文件名、加载数量和 `Sequence replayed from corpus file` 行。
- 对照中的 Echidna `prefix` 精确匹配当前属性名，避免 Harness 里的其他属性影响单属性预算和 `stopOnFail` 结果。测试上限组使用 `testLimit=80`、`stopOnFail=false`；时间组使用每属性 60 秒端到端预算、`testLimit=10,000,000`、`stopOnFail=true`。V2 时间组先扣除种子准备时间，再把剩余时间交给 Echidna。

## 校正记录与复现

首轮对照曾把 `prefix` 设为 `echidna_`，导致 Echidna 同时评估 Harness 内全部属性；Immutable 的耗时 campaign 因其他属性失败而过早结束。首轮原始结果和全部种子、调用成本仍保留，但其对照 campaign 已标记为被校正结果取代。随后将 prefix 改为固定目标属性名，在不重新调用 Agent、不改变已有种子和样本的条件下重跑所有 Echidna 配对。校正原因和前后报告互相链接记录在结果 JSON 中。

## 下一步最值得改进的问题

先修复 EVM 有效性，而不是扩大 API 调用数。Immutable 的 Agent B 在一次执行反馈修复后，`approve` 仍因 token 不存在回滚；后续应结合部署后的实际 mint 状态、目标 Harness 语义和逐交易失败位置改进参数/序列反馈，并保持失败项进入分母。等 EVM 可执行率稳定后，再对固定属性重复多随机种子运行，并把 fresh Slither 分析时间纳入端到端预算，判断同测试数下的覆盖增益能否抵消种子准备开销。
