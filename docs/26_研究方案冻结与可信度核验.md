## 冻结的研究主线

主线固定为：

**安全属性分析 → Agent A/B 多交易规划及参数生成 → Anvil 实际执行反馈与跨交易参数修复 → 有效种子验证 → Echidna 模糊测试。**

允许在这条主线中改进对已有事件、getter、返回值、Slither 守卫和失败 trace 的解释，修复已有流程的可信度口径。禁止加入新的 Agent、属性分组、覆盖贪心选种、语料调度器或其它并行决策模块。

正式研究问题固定为：在不改 Harness、目标属性和真实项目合约的情况下，基于事件、getter、Slither 和真实失败结果的有界跨交易约束处理，能否提高独立项目上的有效序列及目标状态到达率，并在相同 Echidna 预算下产生超出种子单独回放的新路径？

### 方法模块与候选贡献

| 候选贡献 | 定义 | 当前证据状态 |
|---|---|---|
| C1：执行观察驱动的跨交易约束解析 | 使用前序交易事件/返回值、公开 getter、状态差、Slither 守卫及失败 trace 推断对象和数值参数；仅修复受影响参数，保留成功前缀，有限修复后完整重放确认。 | Phase25 四个固定诊断样本均有 Anvil G1 目标状态到达证据；Phase26 仅复核既有种子 fuzz，未验证独立项目泛化。 |
| C2：按执行阶段归因的种子评估协议 | 分开记录 Anvil 目标状态、Echidna 种子回放覆盖、后续 fuzz 新增覆盖、最终覆盖及耗时；不把 corpus 日志或 Anvil 成功等同于 Echidna 目标状态。 | Phase26 的分阶段 LCOV 与调用轨迹证明确有必要；协议学术新颖性和独立任务效用尚未验证。 |

这两个候选不是已成立的论文贡献。若后续留出任务不能重复产生目标状态到达收益，或新增覆盖仅来自种子回放而非后续变异，应收窄或放弃相应主张。

### 已知失败类型

1. 对象未创建、对象 ID 缺失、前序同名字段不唯一或 ABI 类型不匹配。
2. 转账/退款金额超过余额或额度；公开 getter 不足以确定真实约束，或 Slither 表达式无法唯一绑定到事件对象。
3. 外层交易回执成功，但 Harness 捕获了内部回滚。
4. sender、owner、operator、from 地址与当前对象状态不一致。
5. 交易产生状态变化，但没有建立属性相关目标状态。
6. trace 不可用、RPC 传输失败、编译失败或配置不一致。
7. Echidna 外部语料被加载并重放，但该重放是否执行了目标状态、是否在回放末态检查了属性，必须以单独证据验证。
8. 最终 LCOV 是回放与变异的合并结果；没有 seed-only 对照时，不能把最终覆盖增量归因到后续变异。
9. Echidna 输出 `Sequence replayed from corpus file` 只说明尝试回放；覆盖注释中的 `r` 才表明对应 EVM 执行以 revert 结束。回放交易数、路径行命中及属性报告必须分别解读。

## OpenNFTs：已知证据与核验假设

目标属性位于 OpenNFTs Echidna Harness：echidna_balance 检查 balanceOf(address(1)) < 1。Harness 构造器只初始化 owner/treasury；没有给 address(1) 铸币。真实 mint 实现对调用者增加 tokenId，并把 NFT 铸给 msg.sender。真实 transferFrom 在 from 等于 token owner 时增加接收者余额、更新 token owner 并发出 Transfer。

Phase25 Anvil G1 的三次重放均成功：固定 sender 为 `0x…010000`；mint 的 `Transfer` 事件给出 tokenId 1；后续 `transferFrom` 参数为 from=`0x…010000`、to=`0x…0001`、tokenId=1；无内部或外层回滚；交易后 ownerOf(1)=address(1)、balanceOf(address(1))=1，属性从 true 变 false。Phase25 原始尝试文件和逐次结果路径见 Phase25 汇总中的 `replay_runs`。原 Harness、真实合约源码和属性都未修改。

Phase25 Echidna 输入的两个交易与 Anvil G1 一致，配置中的 contractAddr、deployer、psender 和 sender 集合也一致。Phase25 只保存了混合种子与 fuzz 的最终 LCOV，无法判断转账状态写入是否执行。

Phase26 的独立 seed-only replay 在三个随机 seed 下都加载并打印回放成功，但目标源码覆盖注释在 `OpenERC721._transferFrom` 第171行 `require(from == ownerOf(tokenID))` 标记 `*r`；第178–180行余额和 owner 写入均未命中。Echidna 官方 README 定义 `r` 为执行以 REVERT 结束。[Echidna README](https://github.com/crytic/echidna)。因此 `Sequence replayed` 不是交易成功证明，`echidna_balance: passing` 也不是 Anvil 目标状态在 Echidna 中复现的证明。

同一固定 Harness、sender、部署地址、源码、参数及 tokenId 在 Anvil 通过，而 Echidna 的回放在 owner 守卫处失败。现有 trace 没有输出回放时的 ownerOf(1) 和实际 msg.sender，故已定位到具体失败守卫，但还不能进一步断定差异来自 Echidna transaction sender 解释还是回放状态。Phase26 不改属性、Harness 或合约，也不做猜测性修复。完整对照证据见[诊断结果](../deepseek/结果/Phase26研究主线与可信度核验-20261117/诊断证据/OpenNFTs-testLimit0-no-export/诊断结果.json)。

Phase26 只增加 Echidna 执行目录隔离，未更改 Harness、属性语义或真实项目 Solidity 源码。

### OpenNFTs 状态核验结论

- Anvil G1：3/3 目标交易成功，事件和 getter 确认 tokenId 1 属于 address(1)，`balanceOf(address(1))=1`，属性转假。
- Echidna seed-only：3/3 加载并记录 `Sequence replayed...`，LCOV 均为 107 行/2,573 unique instructions，属性均 passing；覆盖注释显示 `OpenERC721.sol:171` 的 owner guard 以 revert 结束，`_balances`/`_owners` 写入行178–180全未命中。
- Echidna seeded 500：3/3 属性仍 passing，最终 LCOV 181/183/181 行；三次 final 都没有命中第178–180行，目标状态仍未到达。
- 因而“Echidna passing”不是反例，也不表示 seed 成功；它表示此次 fuzz 没有执行出违反属性的状态。已定位的直接失败是 Echidna replay 在 `from == ownerOf(tokenID)` 处 revert。由于日志没有输出 ownerOf(1) 和实际 msg.sender，回放状态差的更底层来源仍未确证。没有修改 Harness/属性/合约源码，也没有针对 OpenNFTs 加临时补丁。

## 结论

1. **现有不同种子：** 四条 Phase25 Anvil-valid 种子，内容哈希两两不同；逐条来源与完整参数见冻结输入清单和 Phase25 原始汇总。Echidna 中的有效性需单独按目标状态判断，OpenNFTs seed 不满足该项。
2. **全部直接合并是否优于 native：** 四个固定开发样本中，同预算 seeded final 线覆盖均值都高于 native，12/12 配对差为正；但样本不是独立留出，且 OpenNFTs 的种子回放没有达到目标状态。只能称为本轮方向性证据，不能推广为主线普遍收益。
3. **覆盖贡献选择优于随机选择：** Phase26 没有执行覆盖贪心选择或随机选种对照；Phase24 之前的证据不能替代独立验证。本阶段不支持此类选择器，也不加入调度模块。
4. **后续变异是否产生新路径：** 是。12/12 seeded run 的最终 LCOV 都出现回放阶段以外的新源码行，均有 500 cases 和正数 mutation 日志；OpenNFTs 新增行仍未包含目标余额/owner 写入路径。
5. **是否值得继续反馈式调度：** 不值得在当前证据上开发调度器。现有阶段只验证分阶段测量必要性与固定样本的方向性 coverage gain；候选贡献 C1 的跨项目泛化仍未验证，C2 的论文新颖性未知。下一阶段冻结门发现当前 7 个 V2 注册项目全部已用于 Phase10–25，独立候选为 0。因此在“不找新数据集”约束下，Phase27 不启动正式实验；不追加单合约调参。
