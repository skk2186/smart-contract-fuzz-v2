# Phase 21：实验可信度与目标状态验证

## 目标与范围

本阶段只处理实验可信度和目标状态判定：统一 native/V2 Echidna 配置，复核 OpenNFTs 两条属性的反例语义，为 Anvil 回放添加属性谓词轨迹及直接 getter 证据，并对 Phase 20 的四条既有有效种子做两次小规模配对重复。没有调用 DeepSeek API、生成新种子或修改合约/属性。

## 实现

- `func/功能/种子验证.py` 从 Slither 上下文中的属性源码片段提取谓词调用；对 Harness getter 及其公开地址指向的外部合约 getter，在部署后和每笔成功交易后读取操作数。Anvil 结果新增 `initial_predicate_getters`、逐笔 `predicate_getter_values` 与 `target_property_state`。结果分别标注属性反例是否建立，以及属性谓词操作数是否发生可观测变化，避免把“属性仍为真”误读成“目标相关状态没有变化”。
- `func/测试过程/配对语料可信度实验.py` 读取已有 Agent 结果和种子文件，先在 Anvil 复核，再分别运行空语料 native 与单条 V2 语料。每对复用同一随机种子、sender pool、Harness、deployer、property sender、`testLimit`、`seqLen`、worker、`stopOnFail`、Slither 开关和编译配置；自动检查两臂 YAML 除 `corpusDir` 外一致、编译配置相同。
- 固定输入与测试配置记录在[实验方案](../deepseek/结果/Phase21目标状态配对/实验方案.json)。配对原始数据、配置、每次 Echidna 日志、LCOV 和生成语料位于[paired-2 原始结果](../deepseek/结果/Phase21目标状态配对/paired-2/配对运行结果.json)及同目录；汇总见[配对结果汇总](../deepseek/结果/Phase21目标状态配对/paired-2/配对结果汇总.json)。第一次运行因驱动缺少 timeout 字段未启动 Echidna，完整保存在[paired-1 失败记录](../deepseek/结果/Phase21目标状态配对/paired-1/配对运行结果.json)，不计入配对结果。
- 最终状态分类使用更新后的 Anvil 回放；原始交易与 getter 轨迹在[最终状态复核记录](../deepseek/结果/Phase21目标状态配对/final-state-replay/配对运行结果.json)，精简的逐笔变化在[目标状态汇总](../deepseek/结果/Phase21目标状态配对/final-state-replay/目标状态汇总.json)。

## OpenNFTs 反例语义

`echidna_owner()` 检查 Harness 私有初始地址 `_owner == address(42)` 是否继续等于继承得到的公开 `owner()`。构造器将两者初始化为 `address(42)`，所以部署时属性为 `true`。有效种子由 `address(42)` 调用 `transferOwnership(0x0000000000000000000000000000000000010000)`；`onlyOwner` 通过，事件记录旧 owner 为 `address(42)`、新 owner 为 `property_sender`，交易后 `owner()` 改变，Harness 属性转为 `false`。`OpenERC173.transferOwnership` 正是该合约公开支持的正常所有权转移功能。因此这是**对 Harness 不变式的真实反例**，但仅凭此反例不能报告为权限绕过或合约安全漏洞；若测试意图是验证禁止所有权转移，则该属性与接口语义不符。

`echidna_balance()` 检查 `balanceOf(_other) < 1`，其中 `_other = address(1)`。种子成功执行 `mint(string)`，但 `mint` 将 NFT 铸给 `msg.sender`（`0x...010000`），不是 `address(1)`。新增 getter 证据显示 `balanceOf(address(1))` 部署后与交易后均为 `0`，属性保持 `true`。所以该种子是可执行种子，但没有建立属性违反所需的目标状态；Phase 20 将其 `planned_target_path_reached=true` 计作“末步状态变化”的 proxy，不能视为严格目标路径命中。

## 配对配置与结果

每属性使用 Echidna seed `20261130`、`20261131` 各运行一对，共 8 对、16 个 campaign。每臂 `testLimit=80`、`seqLen=8`、`shrinkLimit=1`、单 worker、property mode、`stopOnFail=false`、禁用内置 Slither。native 臂语料为空；V2 臂只放对应的 Phase 20 有效种子。两臂 sender pool 从同一 Phase 20 属性记录读取，因此 owner 角色 `address(42)` 在 native 和 V2 中都可用。8/8 配置校验通过；V2 种子加载、回放和变异证据均为 8/8。所有 16 个 campaign 都完成 80 个 fuzzing case。

| 属性 | Anvil 目标状态证据 | native unique instructions（seed 30 / 31） | V2 unique instructions（seed 30 / 31） | 属性结果 |
|---|---|---:|---:|---|
| OpenNFTs `echidna_owner` | `true → false`，首次在交易 1；owner 从 `address(42)` 变为 `property_sender` | 4082 / 4837 | 771 / 771 | native 两次 passing；V2 两次 falsified |
| OpenNFTs `echidna_balance` | `true → true`；`balanceOf(address(1))` 为 `0 → 0`，未观察到谓词操作数变化 | 4170 / 5047 | 4481 / 5047 | 两臂均 passing；目标余额未建立 |
| Request `echidna_token_conservation` | `true → true → true`；`totalSupply` 从 `10^25` 增至 `1.00000015×10^25`，Harness 余额和商户/手续费余额同步变化，守恒仍成立 | 18655 / 16835 | 19716 / 17896 | 两臂均 passing；V2 指令数两次各增加 1061 |
| Kink `echidna_token1_conserved` | `true → true → true`；交易 2 后 Harness 与 pool 的 token1 余额重新分配，二者之和仍等于 `initialToken1=10^24` | 10318 / 10452 | 10323 / 10333 | 两臂均 passing；差值分别 +5、−119 |

按新增判定，4 条有效种子中 3 条建立了属性相关的可观测状态（OpenNFTs owner、Request、Kink），其中 1 条使属性变假；OpenNFTs balance 的 `mint` 成功且交易发生，但观察到的目标余额始终为零，属性操作数未变化。这个分层口径把“到达相关状态”与“违反属性”分开：Request 和 Kink 的余额/供应状态确实变化，却没有违反守恒条件。它衡量的是谓词源码可解析 getter 的变化，不能单独证明到达了某个未显式建模的深层分支。

OpenNFTs owner 的 V2 指令数低于 native，是因为语料直接触发属性失败；不应解释为覆盖退化。更关键的是，在统一加入 `address(42)` 后，native 两个 80-case campaign 仍未随机找到该属性反例，而同 seed 的 V2 语料两次均重放并触发。这个结果支持该种子能更直接地到达 Harness 反例状态，但不把允许的 owner 转移误判为漏洞。

Phase 20 使用不同随机种子，且 owner 原生基线缺少 `address(42)` sender；旧的 OpenNFTs native/V2 覆盖数字不能用于严格因果比较。本阶段的配对重复修正了 sender pool 混杂。Request 两次都增加 1061 条 unique instructions；Kink 的差值一正一负，说明收益依赖样本和随机轨迹。每项只有两个重复，不作统计显著性或稳定收益主张。新配对批次没有 DeepSeek API 调用。

## 局限与后续

当前观察器覆盖属性源码中可解析的直接 view 调用、Harness 公开 getter 指向的外部合约 ABI getter，以及简单常量/公开 getter 参数。任意内部 helper、映射索引推导、复杂算术/条件表达式和无公开 getter 的私有状态尚不能完整追踪；“3/4 相关状态变化”只适用于本阶段固定的四条种子与可观测 getter。属性为 `true` 只能说明该时点未违反属性；getter 变化也不等价于目标分支覆盖或漏洞成立。

下一步应保持该配置配对方式，先扩展外部合约 getter 与事件/返回值状态绑定，再在更多属性上做预登记的少量重复；反例需要继续区分“断言被违反”和“违反代表安全问题”。
