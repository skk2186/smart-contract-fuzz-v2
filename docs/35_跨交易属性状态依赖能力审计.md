## 3. 核心源码审查

### 3.1 状态依赖与候选交易

`属性分析适配器.py` 会从属性读取状态、从 Slither 函数效果提取写入状态，并把与目标状态相交的动作列为候选。B 的读状态闭合为 `stage`、`executionLimit`、`completedAmount`；原始候选写入证据把 `createTask` 连到 `stage`，`configureTask` 连到 `stage/executionLimit`，`executeTask` 连到 `stage/completedAmount`。改名后，对应关系仍能按状态读写识别。

C 的静态分析识别 `authorizedOperator`、`depositedCredit`、`executedFor`，并把 `msg.sender` 记录为环境读取；同时声明 mapping 索引别名没有求解。D 识别 `balanceOf`、`totalSupply`、`totalGranted`、`delegatedSpent`；`mint`、`approve`、`transferFrom` 都是属性相关的候选动作，但属性读写分析没有证明具体 owner/spender 键值相同，属性本身也没有读取 `allowance`。本轮 Agent A/B 各一次生成的 C/D 序列仍正确绑定了 owner/operator 与 owner/spender，并由隔离 Anvil getter 复核达到目标。这证明诊断上下文和 Agent 一次性规划能处理这两种结构；不能归功于 E3，也不能据此推断 E3 能补全缺失授权步骤。

`AgentA` 提示规划前置动作；`AgentB` 的提示和本地 validator 都要求逐笔保持 A 的函数顺序，禁止增删交易。因此 Agent B 参数修复不能补上缺失函数。`跨交易状态约束.py` 从前序事件字段、getter 结果、Slither 守卫和失败文本匹配对象值或有限数值边界，也不做交易插入或一般化 guard 求解。B/C/D 的一次 Agent A/B 流程均用了两次请求且没有重试；三条初始候选已各自达到冻结状态，E2 没有参数修复。

### 3.3 候选回放隔离

`replay_seed()` 每个候选先取 Anvil snapshot、部署新目标，再在 `finally` 路径回滚 snapshot；Phase32 对照为 E3/R/S 分别开独立 Anvil session，E3/R/S 从同一冻结序列开始。源码与原始逐笔记录表明扩展候选没有借用其他组的链状态。

## 6. Q2：Agent 规划、参数修复与序列补全的区分

- **Agent A/B 自己规划成功：** B、C、D 的一次性流程各产出三笔序列，并由 Anvil 直接状态读数确认达到各自冻结目标；B 改名变体复用 B 的序列作语义等价核验。A/E 复用历史候选，不计本轮新规划贡献。
- **Agent B 参数修复成功：** B/C/D 的 E2 都没有修复提案，规范化后的交易函数、参数、sender 和 value 与 E1 相同。Agent B 初次参数生成成功，不等于 E2 参数修复有贡献。
- **E3 新增交易步骤成功：** 仅 Wallet 得到实测正例。E3 在 10 次候选内新增 `refund(0)` 和 `deposit(1)`，Anvil 与 Echidna 均确认目标反例。
- **E3 新增交易步骤成功：** 只有 Wallet 有成功归因。E3 在 10 个候选内插入 `refund(0)` 和 `deposit(1)`，Anvil 与 Echidna 均确认反例。
- **E3 只是重复已有操作：** Pigfox 7/7、B 24/24、D 5/5 候选全由 repetition 产生。B 的新增操作使整条候选回放失败；D 的重复 mint 可完整执行，但 E1 已达标，目标相关的 grant/spent/allowance 不变。改名 B 也重复并失败。C 的 E3 没有候选。
- **无法补全：** 这轮 B/C/D 的 E1 已由 Agent A/B 达到目标，因此不能把它们当成“初始序列缺步骤”的反例，也不能证明 E3 对这些依赖会补全。可确认的是 E3 没有额外贡献；真正缺步骤的正向样本仍只有 Wallet。Wallet 的 R/S 未在预算内到达目标。

## 7. Q3：Wallet 结构性过拟合风险

**已证实：** E3 唯一新增步骤并达到目标的结果仍是 Wallet；胜出候选由整数账户参数 `0 → 1` 和同一共享 ETH 资源地址的正向变化驱动，所有交易 `sender` 都保持同一个地址。R 的 24 个候选未到达反例，S 的两个候选未完整执行。B/C/D 的 Agent A/B 初始规划均能在一次流程中达到人工诊断目标，但它们没有给 E3 留下缺失步骤；B、改名 B、D 的 E3 都只重复现有操作，C 的 E3 无候选。Pigfox 同样没有 E3 新增收益。

**代码证实：** E3 动态角色扩展依赖 native ETH trace，且在纯 sender 身份下会丢弃 sender-only 变化；静态动作插入还能占满动态预算。

**边界：** B/C/D 是人工构造的诊断合约，不是独立真实项目；它们的成功证明本轮一次 Agent A/B 流程能为这些状态机生成可执行序列，不能证明 E3 能补齐同类依赖。C/D 扩展器自动目标观察未覆盖所需 mapping 键，直接 Anvil getter 复核纠正了 E1 目标判断，但这一观察局限本身会削弱 E3 的反馈。Wallet 的成功也从冻结 P1 起点出发，不是从零规划成功。

因此，Phase31 的成功存在明显的 Wallet 结构性过拟合风险；现有数据证明的是“在这种整数账户参数 + ETH 余额变化结构上可补全一次”，没有证明对等价但使用 msg.sender、ERC20 allowance 或普通状态机的任务泛化。

## 8. Q4：后续改进建议（不在本轮实施）

1. **优先补一层面向目标 guard 的依赖闭包。** 当前静态动作只按共享属性状态筛候选，动态扩展只对 native 资金地址做有限角色插入；缺少“哪条 guard 为假、哪个 writer 能把对应键值从假变真、后续哪笔消费该状态”的闭环。应先设计记录守卫、读写状态键、调用者角色、跨合约 receiver 路径和执行变化的结构化依赖图，再由现有 `属性分析适配器.py` 与 `状态反馈序列扩展.py` 消费。下一次消融须预先固定一个 E1 尚未达到目标、但独立 Oracle 已证明可达的 Agent 候选；静态闭包、运行时反馈和二者结合从同一候选起跑，按具体前置状态而非 getter 是否变化判定收益，Oracle 成功序列不得进入扩展输入。
2. **修正候选预算分配。** 目前静态插入先占列表，可能把后续执行反馈候选截断；应在独立冻结后比较均匀分配、动态优先、当前排序三组同预算候选数与目标状态到达数，不能只比提出的候选数。
3. **修正属性距离和重复收益评分。** 解析 `return comparison` 与 `if(comparison)return false` 的属性极性，支持等式边界；重复候选必须以关键前置状态或目标距离的方向性进展为依据。用冻结 truth table、B/D 累积状态和 Pigfox 无收益对照做消融。

## 9. Q5：最终路线与阶段决策

在三种选择中，**选择 C：暂不把当前 E3 扩展机制冻结为可直接进入独立真实合约验证的核心贡献，应重新审视并补强其依赖闭包。** E3 唯一实测新增步骤的目标补全来自 Wallet；B/C/D 的 Agent A/B 均已正确规划并达到目标，不能为 E3 记功。B 与改名 B 的 E3 重复候选完整回放失败，C 无 E3 候选，D 的 E3 仅重复 mint，Pigfox 的 E3 也只有无收益 repetition。源码还确认 E3 资源边限于 ETH，sender-only 角色切换被过滤。

该结论是对 E3 当前研究成熟度的决策，不表示 Agent A/B 无法处理普通状态、`msg.sender` 或 ERC20。相反，B/C/D 一次性规划均成功；但这些人工诊断没有形成 E3 缺步骤测试，因此仍不足以断言 E3 对这些类型必然失败。当前不进入独立真实项目验证，先以目标 guard、读写键、账户角色与资源类型为中心补齐机制，并针对真正缺失前置状态设计冻结消融。

**不进入 Phase33，不实施算法改进，不开展下一批真实项目实验，不推送 Git。** 当前可提出的一个核心机制优先项是：建立以目标属性 guard 为中心、带状态键/角色/资源类型/receiver 的跨交易依赖闭包，让静态写者、执行反馈和序列插入基于同一前置状态证据协同工作。
