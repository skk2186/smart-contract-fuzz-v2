# `pipeline-summary.json` — the figures, written down where they were measured

A pipeline's figures live for the length of a CI log and then vanish. Anything
that wants to show them — a page, a README, a report — has to copy them by hand,
and a hand-copied figure rots silently.

It already has. `pigfox.com/how-smart-contracts-are-tested` went on stating four
repositories and twenty-two properties long after both were wrong, on a page
whose entire subject is not trusting a figure nobody checked. The numbers were
measured honestly; then two demos shipped and the table did not move.

So this file exists: a committed, machine-readable record of what the pipeline
measured, **pegged to the source it measured**, generated by
`scripts/pipeline-summary.py`.

> **Status.** Generation only. There is deliberately **no verification gate yet**
> and the `v1` tag has **not** moved. See [Rollout order](#rollout-order) — doing
> either before every repo carries a summary fails all of them at once.

---

## The peg is a pair of TREE shas, not a commit sha

The obvious design is "record the commit hash, and have the gate check it matches
the commit being built". **That is unsatisfiable**, and it is worth understanding
why before anyone tries it again.

A commit's hash is computed over its tree. The tree contains every tracked file,
including this one. So writing `pipeline-summary.json` changes its blob, which
changes the tree, which changes the commit sha — the very value the file was
supposed to contain. The constraint is circular:

```
$ git cat-file -p HEAD
tree cec6e45231878e0a4c022e397500614bd40138e3   <- every tracked file lives here
...
```

What **is** satisfiable is pegging to the content hashes of the inputs the
pipeline actually verified:

```json
"peg": {
  "srcTree":  "git rev-parse HEAD:src",
  "testTree": "git rev-parse HEAD:test"
}
```

A later check recomputes both and compares. This is:

- **self-consistent** — nothing in the file feeds back into the hashes it records;
- **stable across history rewrites** — a rebase or force-push changes commit shas
  but not tree content, so the peg survives;
- **correctly insensitive to irrelevant commits** — editing a README does not
  invalidate figures about `src/` and `test/`, which a commit-sha peg would.

## What this file does NOT claim, and why that matters

**It does not say the pipeline passed, and it cannot.**

The reusable workflow runs with `permissions: contents: read`. CI therefore
cannot commit this file back, so it is generated **locally by a human** and
committed like any other file. There is no branch protection on these
repositories: a push goes straight to `main`.

That leaves a real hole. A developer whose local run is green can commit a
summary alongside a change that goes **red in CI**. The peg is still honest — the
figures do describe that source — but the repository is broken and the file says
nothing about it.

**Therefore: any consumer that displays these figures MUST gate them on the
repository's CI badge**, which is a different source that the generating machine
does not control:

```
https://github.com/pigfox/<repo>/actions/workflows/ci.yml/badge.svg
```

If the badge is not `passing`, the figures must be suppressed rather than shown.
There is deliberately **no `passed` field in the schema** for a consumer to
mistake for that guarantee. A peg proves *description*; only the badge speaks to
*passage*.

## Schema

`schema: "pigfox-pipeline-summary/v1"`

| Field | Source | Notes |
| --- | --- | --- |
| `peg.srcTree`, `peg.testTree` | `git rev-parse HEAD:src`, `HEAD:test` | The whole point. See above. |
| `generatedAt` | clock | UTC, second precision. |
| `tests` | **`forge test --json`** | `suites`, `passed`, `failed`, `skipped`. Parsed from JSON, not from the console summary, whose shape has changed between forge releases. |
| `coverage.files[]` | `coverage-summary.txt` | **Per file**, all four metrics. A single estate-wide percentage is the shape that rots; a per-file list can be checked against the tree. |
| `coverage.namedExclusions` | caller | Empty unless the repo declares one. An exclusion is named, never folded into a percentage. |
| `slither` | **`slither --json -`** | `findingsAtFailOnLow` plus the full `byImpact` breakdown. Slither exits non-zero when it has findings, so its exit code is not treated as an error here — only unparsable output is. |
| `echidna`, `medusa` | engine transcripts | `registeredPassing`, `registeredFailing`, `calls`. |
| `toolchain` | `--version` of each | A figure is only reproducible against the toolchain that produced it, which is why the pipeline pins them. |

### The one asymmetry, stated rather than hidden

Both fuzzers are **text-parsed**, and that is not for want of trying:

- **Echidna** *does* support `--format json`.
- **Medusa** supports nothing but `--no-color`.

Reading Echidna's ordinary transcript rather than running a second
JSON-formatted campaign is a deliberate trade: the numbers are already in the
file the gate just produced, and a second hundred-thousand-call run to re-learn
them would cost minutes for nothing. The regexes used are the same shapes
`scripts/property-count.sh` already asserts against — so an engine whose output
format changes fails the **gate**, loudly, before it can quietly mislead this
generator.

### Fails loudly, never quietly

Every input is required; every parse is checked. A missing transcript does not
become `"calls": 0`. A zero that means *not measured* is exactly the shape of the
stale-artifact bug the property-count gate exists to catch — it once shrank a
five-property set to four and reported a green run. On any failure the generator
writes nothing and exits non-zero:

> `Nothing written. A summary with a guessed figure is worse than none.`

## Generating it

Run the pipeline locally first — the generator consumes the artefacts the gates
produce, and refuses to invent them:

```bash
rm -rf crytic-export && forge build --force
lib/solidity-pipeline/scripts/coverage.sh
echidna . --contract Properties --config echidna.yaml | tee echidna-output.txt
medusa fuzz --config medusa.json 2>&1 | tee medusa-output.txt

lib/solidity-pipeline/scripts/pipeline-summary.py
```

Then commit `pipeline-summary.json` with the change it describes.

`pipeline-summary.py` is the only Python in this repository. It reads JSON and
writes JSON; doing that in bash would need `jq`, which the pipeline does not
install and which would become a new dependency of every consuming repo.

## Rollout order

**Order matters, and getting it wrong breaks every repository at once.**

1. **Generation lands first, unverified.** ← *this step is done for one repo*
   The script exists in the pipeline; one repo carries a summary. The file is
   inert data. No gate reads it, so nothing can fail because of it.
2. **Every repo commits a summary.** Still no gate. At the end of this step all
   six repositories have the file and it is current.
3. **Only then does the verification gate land**, as a new job in `solidity.yml`
   that recomputes the tree shas and fails on a mismatch — and only then does the
   `v1` tag move to pick it up.
4. **Only then does a consumer display the figures**, badge-gated per the section
   above.

Moving `v1` at step 1 or 2 would fail all six repositories simultaneously, for
the entirely correct reason that five of them have no summary yet. The tag is a
shared moving reference — at the time of writing `v1` is one commit behind this
repository's `main`, so moving it is a deliberate act with estate-wide blast
radius, not a routine bump.
